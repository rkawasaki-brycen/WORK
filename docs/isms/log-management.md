# ログ管理ポリシー

## 目的

本文書は、システムおよびアプリケーションのログを適切に収集・保管・保護・活用するための方針を定める。ログはセキュリティインシデントの検出・調査、コンプライアンス要件の充足、および運用上の問題解決に不可欠な情報基盤である。

## 適用範囲

- アプリケーションログ（API、バックエンド、フロントエンド）
- セキュリティログ（認証、認可、アクセス制御）
- 監査ログ（操作履歴、設定変更）
- インフラログ（クラウドサービス、ネットワーク）
- GitHub Audit Log

## 1. ログに記録すべき情報

### 1.1 認証・認可イベント

以下のイベントはすべてログに記録しなければならない。

| イベント種別 | 記録内容 |
|---|---|
| ログイン成功 | タイムスタンプ、ユーザーID、IPアドレス、User-Agent、認証方式 |
| ログイン失敗 | タイムスタンプ、試行したユーザーID/メール、IPアドレス、失敗理由 |
| ログアウト | タイムスタンプ、ユーザーID、セッションID |
| パスワード変更 | タイムスタンプ、ユーザーID、操作元（本人/管理者） |
| MFA検証 | タイムスタンプ、ユーザーID、成否、方式 |
| セッションタイムアウト | タイムスタンプ、ユーザーID、セッションID |
| 権限昇格 | タイムスタンプ、ユーザーID、昇格前後のロール、理由 |
| アクセス拒否 | タイムスタンプ、ユーザーID、リソース、拒否理由 |

### 1.2 データアクセスイベント

機密データへのアクセスは記録する。

| イベント種別 | 記録内容 |
|---|---|
| 個人情報の参照 | タイムスタンプ、操作者ID、対象リソース、操作種別（READ）|
| 個人情報の更新・削除 | タイムスタンプ、操作者ID、対象リソース、操作前後の差分（必要に応じて）|
| 一括データエクスポート | タイムスタンプ、操作者ID、対象データ範囲、件数 |
| APIによるデータアクセス | タイムスタンプ、APIキーID（ハッシュ）、エンドポイント、操作種別 |

**注意:** ログにパスワードや個人情報（PII）そのものを記録してはならない。識別子（ユーザーID、ハッシュ等）を使用する。

### 1.3 システムイベント

| イベント種別 | 記録内容 |
|---|---|
| アプリケーション起動・停止 | タイムスタンプ、サービス名、バージョン |
| 設定変更 | タイムスタンプ、操作者ID、変更項目、変更前後の値 |
| デプロイ実施 | タイムスタンプ、デプロイ者、バージョン、環境 |
| スケジュールジョブの実行 | タイムスタンプ、ジョブ名、実行結果、処理件数 |
| 外部サービス連携エラー | タイムスタンプ、サービス名、エラーコード、メッセージ |

### 1.4 エラー・例外

| ログレベル | 記録基準 | 記録内容 |
|---|---|---|
| ERROR | 処理が失敗し、ユーザー/システムへの影響がある | エラーメッセージ、スタックトレース、リクエストID、ユーザーID |
| WARN | 処理は完了したが、注意が必要な状態 | 警告内容、関連コンテキスト |
| INFO | 正常な業務上重要な操作 | 操作内容、関連ID |
| DEBUG | 開発・デバッグ時の詳細情報 | **本番環境では出力しない** |

### 1.5 ログフォーマット

ログは構造化された形式（JSON）で出力し、後処理での検索・集計を容易にする。

```json
{
  "timestamp": "2026-06-12T10:30:00.000Z",
  "level": "INFO",
  "service": "api-server",
  "version": "1.2.3",
  "traceId": "abc123def456",
  "userId": "user_xyz",
  "event": "auth.login.success",
  "ip": "203.0.113.1",
  "userAgent": "Mozilla/5.0 ...",
  "durationMs": 45,
  "message": "ログイン成功"
}
```

## 2. ログの保管期間

### 2.1 保管期間の定義

| ログ種別 | 保管期間 | 根拠 |
|---|---|---|
| **アプリケーションログ**（通常の操作ログ、エラーログ） | **90日** | 運用調査・トラブルシューティング用途 |
| **セキュリティログ**（認証・認可・アクセス制御） | **1年** | セキュリティインシデント調査・コンプライアンス |
| **監査ログ**（設定変更・権限操作・データ操作履歴） | **3年** | 法的・コンプライアンス要件、内部監査 |
| GitHub Audit Log | GitHubポリシーに準拠（Enterprise: 1年以上） | 開発・リポジトリ操作の追跡 |
| インフラログ（クラウドサービスのアクティビティログ） | **1年** | セキュリティ調査・コンプライアンス |

### 2.2 保管場所

| ログ種別 | プライマリ保管場所 | バックアップ |
|---|---|---|
| アプリケーションログ | クラウドログサービス（CloudWatch Logs等） | S3/GCS（長期保管用） |
| セキュリティログ | SIEM または専用ログ管理サービス | S3/GCS（暗号化・不変ストレージ） |
| 監査ログ | 専用監査ログサービス（不変ストレージ） | 別リージョンへの複製 |
| GitHub Audit Log | GitHub Enterprise（組織設定でエクスポート） | S3/GCS（定期エクスポート） |

### 2.3 ストレージコスト最適化

保管コストを最適化するため、以下の階層化ストレージ方針を適用する。

- **0〜30日:** ホットストレージ（即時検索可能）
- **31〜90日:** ウォームストレージ（分単位でアクセス可能）
- **91日以降:** コールドストレージ（時間単位でアクセス可能、コンプライアンス対応）

## 3. GitHub Audit Logの活用

### 3.1 監視すべきイベント

GitHub Audit Log では以下のイベントを定期的に確認する。

| カテゴリ | 監視対象イベント |
|---|---|
| **リポジトリアクセス** | リポジトリの公開設定変更、アーカイブ、削除 |
| **メンバー管理** | 組織メンバーの追加・削除、ロール変更 |
| **Secrets管理** | Secretsの作成・更新・削除 |
| **ブランチ保護** | ブランチ保護ルールの変更 |
| **OAuth App** | OAuth Appの認可・取り消し |
| **Personal Access Token** | PATの作成（Finegraind PAT使用を推奨） |
| **Actions** | Actionsの有効化・無効化、ワークフロー権限変更 |
| **Webhook** | Webhookの作成・変更・削除 |

### 3.2 GitHub Audit Logのエクスポート設定

```bash
# GitHub CLI を使用したAudit Logのエクスポート（月次）
gh api \
  -H "Accept: application/vnd.github+json" \
  "/orgs/{org}/audit-log?phrase=action:repo&per_page=100" \
  --paginate > github-audit-$(date +%Y%m).json
```

組織設定での自動エクスポート（GitHub Enterprise）:
- Organization Settings → Audit log → Export
- S3またはAzure Blob Storageへの継続的ストリーミングを設定する

## 4. ログレビュープロセス

### 4.1 定期レビュースケジュール

| レビュー頻度 | 担当 | 確認内容 |
|---|---|---|
| **日次** | オンコール担当 | アラートおよび異常なエラー率の確認 |
| **週次** | Security担当 | 認証失敗の傾向、不審なアクセスパターン |
| **月次** | Tech Lead + Security Lead | セキュリティログの総合レビュー、GitHub Audit Log確認 |
| **四半期** | Tech Lead + CTO | 監査ログのコンプライアンスレビュー、保管ポリシーの見直し |

### 4.2 アラートの設定

以下の条件でアラートを設定し、Slackの `#security-alerts` チャンネルに通知する。

| アラート条件 | 重要度 | 対応 |
|---|---|---|
| 同一IPからの認証失敗が5分間で10回以上 | High | 即時調査・当該IPの一時ブロック検討 |
| 管理者アカウントへの認証失敗 | High | 即時調査 |
| 深夜（0:00〜6:00 JST）の管理者操作 | Medium | 翌営業日に確認 |
| 大量データエクスポート（1,000件超） | Medium | 当日中に確認 |
| セキュリティルールの変更 | High | 即時確認 |
| エラーレートが過去1時間の平均の3倍超 | Medium | 即時調査 |

### 4.3 ログレビューチェックリスト（月次）

```
□ 認証失敗の異常なスパイクがないか
□ 通常とは異なる時間帯・場所からのアクセスがないか
□ 退職済みアカウントのアクティビティがないか
□ 権限昇格操作が適切に記録されているか
□ データエクスポート操作が業務上妥当なものか
□ GitHub Audit Log に未承認のリポジトリ設定変更がないか
□ Secrets の操作履歴に不審なものがないか
□ ログの欠損期間がないか（ログ収集の継続性確認）
□ SIEMのアラートが適切に対応されているか
```

## 5. ログの保護

### 5.1 不変性の確保

ログが改ざんされないよう、以下の措置を講じる。

**技術的対策:**
- **Write Once Read Many (WORM) ストレージ**の使用（S3 Object Lock、GCS Object Hold等）
- ログの書き込み専用IAMロールを使用し、削除権限を分離する
- 重要なログにはチェックサム（SHA-256）を付与し、整合性を検証できるようにする
- ログストレージへのアクセスにはMFAを必須とする

**設定例（AWS S3 Object Lock）:**
```json
{
  "ObjectLockEnabled": "Enabled",
  "Rule": {
    "DefaultRetention": {
      "Mode": "COMPLIANCE",
      "Days": 365
    }
  }
}
```

### 5.2 アクセス制御

ログへのアクセスは最小権限の原則に基づき制限する。

| ロール | 読み取り | 書き込み | 削除 |
|---|---|---|---|
| アプリケーション（ログ送信） | - | 許可 | 禁止 |
| 開発者 | アプリ・セキュリティログ（90日以内） | 禁止 | 禁止 |
| Tech Lead | すべて | 禁止 | 禁止 |
| Security Lead | すべて | 禁止 | 禁止 |
| 監査担当（CTO/外部監査） | 監査ログ | 禁止 | 禁止 |
| インフラ管理者 | すべて（緊急時のみ） | 設定のみ | コンプライアンス期間後のみ |

### 5.3 暗号化

- 転送中のログは TLS 1.2以上で暗号化する
- 保管中のログはサーバーサイド暗号化（SSE-KMS等）を使用する
- 監査ログの暗号化キーは、ログ自体とは別に管理する

### 5.4 個人情報（PII）の取り扱い

ログに個人情報が含まれる場合は以下の措置を講じる。

- ログ収集前にIPアドレスをマスキング（例: `203.0.113.xxx`）する
- ユーザーの本名・メールアドレスの代わりにユーザーIDを使用する
- 個人情報を含む可能性のある自由入力フィールドはログに含めない
- GDPRなどの規制に基づく削除要求に応じられるよう、PII含有ログの検索・削除手順を整備する
