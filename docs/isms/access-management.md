# アクセス管理ポリシー

## 目的

本ポリシーは、組織のシステム・サービス・情報資産へのアクセスを適切に管理し、不正アクセスおよび情報漏洩のリスクを最小化することを目的とします。

## 適用範囲

本ポリシーは、組織に所属するすべての社員・契約社員・業務委託先、および組織のシステム・サービスにアクセスするすべての第三者に適用されます。対象システムには GitHub、クラウドインフラ、SaaS ツール、社内システムが含まれます。

---

## 最小権限の原則

組織はすべてのアクセス管理において**最小権限の原則 (Principle of Least Privilege)** を適用します。

### 基本方針

- **必要最小限のアクセス**: 職務を遂行するために必要な最小限のアクセス権限のみを付与する
- **デフォルト拒否**: 明示的に許可されていない操作はすべて拒否する
- **時限的アクセス**: 一時的な業務のために付与したアクセスは、業務完了後速やかに取り消す
- **権限分離**: 重要な操作は複数の担当者に分担させ、単一人物による全権掌握を防ぐ
- **定期的な棚卸し**: 付与した権限が引き続き必要かどうかを定期的に確認する

### 実装ガイドライン

1. 新規メンバーへの初期権限は最低限のレベルから開始し、業務上の必要に応じて段階的に拡張する
2. ロールベースのアクセス制御 (RBAC) を使用し、個人ではなくロールに権限を付与する
3. 共有アカウントは原則使用しない。やむを得ない場合はサービスアカウントを使用し、責任者を明確にする
4. 管理者権限は業務上不可欠な場合のみ付与し、日常業務には一般権限を使用する

## アクセス申請・承認ワークフロー

### 通常のアクセス申請

```
申請者が申請フォームに記入
       |
  直属の上長がレビュー・承認
       |
  システムオーナー / セキュリティ担当者が審査
       |
  技術担当者がアクセス権を設定
       |
  申請者に通知・確認
       |
  アクセス台帳に記録
```

### 申請に必要な情報

アクセス申請時には以下の情報を提出します。

| 項目 | 説明 |
|-----|------|
| 申請者氏名 | フルネーム |
| 対象システム | アクセスが必要なシステム・リソース名 |
| 要求する権限レベル | 具体的な権限 (例: GitHub の Write 権限) |
| 必要な理由 | 業務上の必要性を具体的に説明 |
| 期間 | 永続的 / 一時的 (一時的な場合は終了日を明記) |
| 承認者 | 直属の上長またはプロジェクトオーナー |

### 承認フロー

| 権限レベル | 承認者 |
|-----------|-------|
| Internal レベルのリソース | 直属の上長 |
| Confidential レベルのリソース | 直属の上長 + システムオーナー |
| Restricted レベルのリソース | 直属の上長 + システムオーナー + ISMS 管理責任者 |
| 管理者権限 (Admin) | ISMS 管理責任者 |

### 申請から付与までの目標時間

| 権限レベル | 目標時間 |
|-----------|---------|
| Internal / Confidential | 1 営業日以内 |
| Restricted / Admin | 3 営業日以内 (審査が必要なため) |

## GitHub アクセスレベルと使用基準

GitHub では Organization レベルおよびリポジトリレベルの権限を適切に管理します。

### Organization メンバーシップ

| ロール | 対象 | 付与条件 |
|-------|------|---------|
| Owner | ISMS 管理責任者・CTO クラス | 経営層の承認が必要。最小限の人数に限定 |
| Member | 正社員・長期契約社員 | 上長の承認。デフォルトリポジトリアクセスは None |
| Outside Collaborator | 外部委託・パートナー | プロジェクトオーナーの承認。特定リポジトリのみアクセス可 |

### リポジトリ権限レベル

| 権限 | できること | 付与対象 |
|-----|-----------|---------|
| **Read** | コードの閲覧、Issue・PR の閲覧 | 外部レビュア、監査担当者、参照目的のみのメンバー |
| **Triage** | Read に加えて、Issue・PR の管理 (クローズ、ラベル付け等) | プロジェクトマネージャー、QA 担当者 (コードコミット不要な役割) |
| **Write** | Triage に加えて、コードのプッシュ・マージ、ブランチ作成 | 開発に参加するすべてのエンジニア (標準権限) |
| **Maintain** | Write に加えて、リポジトリ設定の一部変更、GitHub Pages の管理 | テックリード、シニアエンジニア (明確な業務必要性がある場合) |
| **Admin** | Maintain に加えて、リポジトリの全設定変更、メンバー管理、保護ブランチルールの変更、リポジトリ削除 | リポジトリオーナー (1〜2 名に限定) |

### GitHub アクセス管理のルール

1. **Protected Branch**: `main` / `master` ブランチは必ず保護ブランチに設定する
   - 直接プッシュを禁止
   - 最低 1 名のレビュー承認を必須とする
   - 全ステータスチェックのパスを必須とする

2. **CODEOWNERS ファイル**: セキュリティに関わるファイル (`.github/`, `infra/`, シークレット設定等) には CODEOWNERS を設定し、変更時に必ずセキュリティ担当者のレビューを要求する

3. **Outside Collaborator**: 外部委託先には必要最小限のリポジトリのみアクセスを付与し、契約終了時は即時削除する

4. **Fine-grained Personal Access Tokens**: PAT は Fine-grained を使用し、Classic PAT は原則使用しない。有効期限は最大 90 日とする

5. **Secrets**: GitHub Secrets に登録する際は環境別 (production/staging/development) に分離し、production シークレットへのアクセスは最小限にする

## サービスアカウント管理

### サービスアカウントの定義

サービスアカウントとは、人間ではなくシステム・アプリケーション・自動化スクリプトが使用するアカウントです。

### 管理ルール

1. **専用アカウント**: サービスアカウントは用途ごとに専用のアカウントを作成し、複数のシステムで共用しない
2. **責任者の明確化**: 各サービスアカウントには必ず担当チームまたは責任者を紐づける
3. **最小権限**: 必要な操作のみを実行できる最小限の権限を付与する
4. **認証情報の管理**: 認証情報はシークレット管理ツール (AWS Secrets Manager, GitHub Secrets, Vault 等) で管理し、コードへの埋め込みは禁止
5. **認証情報のローテーション**: API キー・パスワードは定期的 (最長 90 日ごと) にローテーションする
6. **台帳管理**: すべてのサービスアカウントをアクセス台帳に登録し、定期的にレビューする

### サービスアカウント台帳の記録項目

| 項目 | 例 |
|-----|-----|
| アカウント名 | `github-actions-deploy` |
| 使用システム | GitHub Actions |
| 用途 | 本番環境へのデプロイ |
| 付与された権限 | AWS ECS デプロイ権限 |
| 担当チーム / 責任者 | インフラチーム / 氏名 |
| 認証情報の保管場所 | GitHub Secrets (repository: app-repo) |
| 最終ローテーション日 | 2026-04-01 |
| 次回ローテーション予定日 | 2026-07-01 |

## アクセスレビュースケジュール

### 四半期レビュー (1 月・4 月・7 月・10 月)

毎四半期、以下のアクセス権を棚卸しします。

**対象**
- GitHub Organization のメンバーシップおよびリポジトリ権限
- クラウドインフラの IAM ロール・ポリシー
- SaaS ツール (Linear, Notion, Slack 等) のユーザーアカウント
- サービスアカウントおよび API キー

**手順**

1. セキュリティ担当者がアクセス台帳を最新化する
2. 各チームリーダーに現メンバーとその必要な権限のリストを確認依頼する
3. 退職済み・異動済みのメンバーの権限が削除されているか確認する
4. 業務上不要になった権限を特定し、削除またはダウングレードする
5. 不審なアクセスパターンがないかログを確認する
6. レビュー結果をドキュメントに記録する

**エスカレーション基準**
- 退職後もアクセスが残存している場合: 即時削除 + ISMS 管理責任者への報告
- 承認なく権限が昇格している場合: 即時調査 + セキュリティインシデントとして記録

## オフボーディングチェックリスト

メンバーが退職・契約終了する場合、最終出社日またはアクセス終了日までに以下の手順を完了します。

### 人事・管理部門の対応

- [ ] 退職・契約終了日を IT/セキュリティ担当者に通知する (最低 3 営業日前)
- [ ] 貸与機器 (PC, スマートフォン等) の返却を確認する
- [ ] 入館証・物理アクセスキーの返却を確認する

### セキュリティ担当者・IT 担当者の対応

**アカウント無効化**
- [ ] GitHub Organization からメンバーを削除する
- [ ] Google Workspace / Microsoft 365 アカウントを無効化する
- [ ] Slack ワークスペースからメンバーを削除する
- [ ] Linear / Notion / その他 SaaS ツールのアカウントを無効化・削除する
- [ ] VPN アカウントを無効化する
- [ ] クラウドインフラ (AWS/GCP/Azure) の IAM ユーザーを削除する

**認証情報の無効化**
- [ ] 当該メンバーが管理していた API キー・シークレットを無効化・ローテーションする
- [ ] 当該メンバーが登録していた SSH 公開鍵をすべて削除する
- [ ] MFA デバイスの登録を解除する
- [ ] 当該メンバーが知っている共有パスワードをローテーションする

**データ・資産の引き継ぎ**
- [ ] 担当プロジェクトの引き継ぎ状況を確認する
- [ ] 組織のデータが個人端末・個人アカウントに残存していないか確認する
- [ ] サービスアカウントの責任者変更が必要な場合は変更する

**確認・記録**
- [ ] 上記すべての対応完了をアクセス台帳に記録する
- [ ] 対応が遅延した場合はリスクを評価しエスカレーションする

### 退職後の対応

- 退職後 30 日間、当該メンバーのアクセスログを監視する
- 不審なアクセスが発見された場合はセキュリティインシデントとして対応する

## 緊急アクセス手順

### 緊急アクセスが必要な状況

以下の緊急事態において、通常のアクセス申請フローを迂回した緊急アクセスが必要になる場合があります。

- 本番システムの重大障害・サービスダウン
- セキュリティインシデントへの対応
- 担当者の急な欠勤・連絡不能による業務継続
- 災害・BCP 発動時

### 緊急アクセスの手順

1. **宣言**: 緊急アクセスが必要であることを ISMS 管理責任者または直属の上長に口頭または Slack で即時報告する
2. **承認**: ISMS 管理責任者または上長が口頭・チャットで承認する (事後承認も可)
3. **アクセス**: 承認を受けた担当者が必要最小限のアクセス操作を行う
4. **記録**: 操作内容・理由・時刻をリアルタイムまたは事後速やかに記録する
5. **事後申請**: 緊急事態収束後 24 時間以内に正式なアクセス申請書を提出する
6. **棚卸し**: 緊急アクセスのために付与した権限は業務完了後速やかに取り消す

### 緊急アクセス時のログ取得

緊急アクセス中は特に以下のログを必ず保持します。

- 実行したコマンド・操作の記録
- アクセスしたリソースのリスト
- 変更を加えた場合は変更前後の状態

### Break-glass アカウント

重大障害時などに通常のアカウントが使用できない場合に備え、Break-glass (緊急用) アカウントを管理します。

- Break-glass アカウントの認証情報は ISMS 管理責任者が管理する封筒・金庫に保管する
- 使用した場合は必ず ISMS 管理責任者に報告し、使用ログを残す
- 年 1 回、認証情報が有効であることを確認する (テストアクセスを実施)
- 使用後は認証情報を必ずローテーションする

## アクセス台帳管理

### 台帳の構成

アクセス台帳は以下のシートで構成します。

1. **ユーザーアクセス台帳**: 全メンバーのシステムごとのアクセス権
2. **サービスアカウント台帳**: サービスアカウント・API キーの一覧
3. **レビュー記録**: 四半期レビューの実施記録
4. **申請記録**: アクセス申請・承認の記録

### 台帳の保管

- アクセス台帳は Confidential レベルで管理する
- セキュリティ担当者のみが編集権限を持つ
- バックアップは定期的に取得する

## 違反と対応

### ポリシー違反の例

- 承認なく他者のアカウントを使用する
- 付与された権限を超えた操作を行う
- アクセス権の申請・変更を虚偽の理由で行う
- 退職後もアカウントを使用する
- 共有パスワードを許可なく他者に教える

### 対応

ポリシー違反が発覚した場合、以下の手順で対応します。

1. 当該アクセスを即時停止する
2. セキュリティ担当者および ISMS 管理責任者に報告する
3. 違反の範囲・影響を調査する
4. 人事手続きを含む適切な措置を講じる
5. インシデントとして記録し、再発防止策を実施する
