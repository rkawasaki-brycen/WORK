# 情報分類ポリシー

## 目的

本ポリシーは、組織が取り扱う情報資産を適切に分類し、その機密性レベルに応じたハンドリングルールを定めることで、情報の不適切な開示・損失・改ざんを防止することを目的とします。

## 適用範囲

本ポリシーは、組織に所属するすべての社員・契約社員・業務委託先、および組織のシステム・サービスにアクセスするすべての第三者に適用されます。

---

## 分類レベル定義

組織の情報は以下の 4 段階に分類されます。

### レベル 1: Public (公開)

**定義**  
公開を前提とした、または公開しても組織・顧客に損害を与えない情報。

**特徴**
- 意図的に外部へ公開される情報
- 漏洩しても実質的な損害が発生しない
- 一般ユーザー向けのマーケティング・広報資料

**例**
- 公開 Web サイト・ランディングページのコンテンツ
- プレスリリース・ブログ記事
- オープンソースとして公開されたソースコード
- 公開 API のドキュメント
- 採用情報

---

### レベル 2: Internal (社内限定)

**定義**  
組織内部での利用を前提とした情報。外部への漏洩は望ましくないが、漏洩しても軽微な損害にとどまる可能性が高い情報。

**特徴**
- 全社員が業務上必要とする可能性がある
- 競合他社・外部への漏洩は避けるべき
- 意図的な公開でない限り外部に共有しない

**例**
- 社内会議の議事録・資料
- 内部向け開発ドキュメント・設計書 (機密情報を含まないもの)
- 社内ロードマップ (公開前)
- 組織図・メンバーリスト
- 社内ポリシードキュメント (本 ISMS 文書含む)
- 一般的な技術仕様・アーキテクチャ図

---

### レベル 3: Confidential (機密)

**定義**  
業務上必要な特定の関係者のみがアクセスすべき情報。漏洩した場合、組織・顧客・パートナーに重大な損害を与える可能性がある情報。

**特徴**
- 職務上の必要性 (Need-to-Know) に基づいてアクセスを制限する
- 外部への共有には明示的な承認が必要
- 暗号化などの技術的保護措置を適用する

**例**
- 非公開のソースコード・プロプライエタリアルゴリズム
- 顧客との契約書・NDA
- 財務情報・事業計画
- 未公開の製品ロードマップ・M&A 情報
- セキュリティ設定・ファイアウォールルール
- バグ報告・脆弱性情報 (修正前)
- 人事情報・給与データ
- パートナー企業の機密情報

---

### レベル 4: Restricted (極秘)

**定義**  
最高レベルの保護を要する情報。漏洩した場合、組織・顧客・個人に深刻かつ回復困難な損害を与える情報。

**特徴**
- アクセスは最小限の特定個人に制限する
- 強力な暗号化・多要素認証を必須とする
- すべてのアクセスをログに記録する
- 紙媒体での取り扱いは原則禁止

**例**
- 認証情報・シークレットキー・API キー・パスワード
- 暗号化キー・証明書の秘密鍵
- 顧客の個人情報 (氏名・住所・電話番号・メールアドレス)
- 顧客の決済情報・クレジットカードデータ
- 医療・健康情報
- 生体認証データ
- 法執行機関との連携情報

## ハンドリングルール

### 保存要件

| レベル | 保存要件 |
|-------|---------|
| Public | 制限なし。標準的なバックアップを推奨 |
| Internal | 組織が管理するシステム (GitHub, Notion, Google Workspace 等) に保存。個人端末への長期保存は避ける |
| Confidential | 組織が管理するシステムに保存し、適切なアクセス制御を設定する。暗号化ストレージを推奨 |
| Restricted | 強制的な暗号化が有効なストレージにのみ保存。シークレット管理ツール (AWS Secrets Manager, GitHub Secrets 等) を必須とする。平文での保存は禁止 |

### 送信要件

| レベル | 送信要件 |
|-------|---------|
| Public | 制限なし |
| Internal | 組織の承認済み通信手段 (Slack, メール等) を使用。個人の通信手段は使用しない |
| Confidential | 暗号化された通信路 (HTTPS, TLS) のみ使用。メール送信時は受信者を慎重に確認する |
| Restricted | 暗号化された通信路を必須とする。メール送信は原則禁止 (やむを得ない場合は暗号化添付ファイルのみ)。送受信のログを保持する |

### アクセス制御要件

| レベル | アクセス制御要件 |
|-------|--------------|
| Public | 制限なし |
| Internal | 組織メンバーのみ。ゲストアカウントへの共有は個別承認が必要 |
| Confidential | 職務上の必要性に基づき個別に権限付与。オーナーによる承認が必要。定期的なアクセスレビューを実施 |
| Restricted | 最小限の指定された担当者のみ。ISMS 管理責任者の承認が必要。MFA 必須。すべてのアクセスをログに記録 |

### 保存期間と廃棄

| レベル | 保存期間 | 廃棄方法 |
|-------|---------|---------|
| Public | 必要な期間 | 通常削除 |
| Internal | 業務上必要な期間 + 1 年 | 通常削除 (論理削除後のデータ復元不可確認を推奨) |
| Confidential | 契約・法令で定められた期間 (最短 3 年) | 安全な削除 (データ上書き・シュレッダー等) |
| Restricted | 法令で定められた最大期間または業務終了後速やかに | 暗号消去または物理破壊。廃棄記録を残す |

## GitHub におけるラベリング規則

### リポジトリトピック (Topics)

リポジトリに以下のトピックを付与することで、そのリポジトリが含む情報の最高分類レベルを明示します。

| トピック | 意味 |
|---------|------|
| `isms-public` | リポジトリ内容は Public レベル (オープンソース等) |
| `isms-internal` | リポジトリ内容は Internal レベル以下 |
| `isms-confidential` | リポジトリ内容に Confidential レベルの情報を含む |
| `isms-restricted` | リポジトリ内容に Restricted レベルの情報を含む (原則禁止、シークレットは別管理) |

**注意**: `isms-restricted` のトピックが付いているリポジトリは、シークレット管理の観点から問題がある可能性を示します。シークレットは必ずシークレット管理ツールで管理し、コードに含めないでください。

### プルリクエストラベル

PR に以下のラベルを付与して、変更内容の機密性を示します。

| ラベル | 色 | 意味 |
|-------|-----|------|
| `security: public` | 緑 (#0e8a16) | セキュリティへの影響なし・公開情報のみ |
| `security: internal` | 青 (#0075ca) | 社内限定情報を含む変更 |
| `security: confidential` | 橙 (#e4a400) | 機密情報に関わる変更・セキュリティレビュー推奨 |
| `security: restricted` | 赤 (#b60205) | 極秘情報・アクセス制御に関わる変更・必須レビュー |

`security: confidential` または `security: restricted` のラベルが付いた PR は、セキュリティ担当者による必須レビューを受けてからマージしてください。

## 誤分類情報の対処方法

### 低く分類されていた場合 (アンダークラシフィケーション)

より高い分類レベルが必要な情報が低く分類されていることが発覚した場合、以下の手順を踏みます。

1. **即時対応**: 発見者は直ちにセキュリティ担当者に報告する
2. **アクセスの一時停止**: 不適切なアクセスが発生している可能性がある場合、速やかにアクセスを制限する
3. **影響調査**: 情報が不適切にアクセス・共有されていないか調査する
4. **再分類**: 正しい分類レベルに変更し、それに応じたハンドリングルールを適用する
5. **記録**: インシデントとして記録し、再発防止策を検討する

### 高く分類されていた場合 (オーバークラシフィケーション)

情報が必要以上に高く分類されており、業務効率に影響している場合、以下の手順を踏みます。

1. **申請**: 情報のオーナーまたは担当者がセキュリティ担当者に再分類を申請する
2. **レビュー**: セキュリティ担当者がリスクを評価する
3. **承認・変更**: 承認された場合、分類レベルを変更し、関係者に通知する

### 外部に誤送信した場合

Restricted または Confidential 情報を権限のない外部に送信してしまった場合、以下の手順を踏みます。

1. **即時報告**: セキュリティ担当者および ISMS 管理責任者に即時報告する
2. **情報の回収**: 受信者に連絡し、情報の削除を依頼する
3. **影響評価**: 個人情報が含まれる場合、個人情報保護法に基づく報告義務を確認する
4. **インシデント記録**: インシデントとして記録し、根本原因を分析する
5. **再発防止**: 送信手順の見直しや教育を実施する

## 情報のライフサイクル管理

情報の分類はライフサイクル全体を通じて適切に管理されます。

```
作成・収集 -> 分類・ラベリング -> 保存・利用 -> 共有・配布 -> 保管 -> 廃棄
     |              |                 |              |            |        |
  オーナー        オーナー         担当者        承認者       担当者   担当者
  が分類を       がラベルを       がルール       が適切性     が保存   が廃棄
  決定する       付与する         を遵守する     を確認する   期間管理  記録を残す
```
