# Linear プロジェクト管理オペレーション

このドキュメントは、WORKチームにおける Linear を用いたプロジェクト管理の運用ルールを定義します。

---

## 1. チーム構成

### メインチーム

- **チーム名**: WORK
- **識別子**: WORK（Linearの Issue ID プレフィックスに使用: `WORK-123`）

### サブチームの考え方

現時点ではサブチームを設けず、単一の WORK チームで運用する。
チームが拡大し、以下のいずれかに該当する場合はサブチームへの分割を検討する。

- メンバーが 10 名を超え、専門領域が明確に分かれた場合
- フロントエンド・バックエンド・インフラで独立したスプリントが必要になった場合

その際のサブチーム候補:
- **WORK-FE**: フロントエンド担当
- **WORK-BE**: バックエンド担当
- **WORK-INFRA**: インフラ・SRE 担当

## 2. ワークフローステート

### ステート一覧と説明

| ステート | 説明 |
|---|---|
| **Backlog** | 起票済みだがまだトリアージされていない Issue。優先度・担当者未確定。 |
| **Triage** | トリアージ中。優先度・担当者・スプリントへの割り当てを判断中。 |
| **Todo** | スプリントに組み込まれ、着手待ち状態。担当者・優先度が確定している。 |
| **In Progress** | 担当者が実装・対応を進めている状態。 |
| **In Review** | 実装完了。Pull Request をオープンしてレビュー待ち。 |
| **Testing** | レビュー承認済み。QA・動作確認中。ステージング環境などで検証中。 |
| **Done** | リリース完了またはタスク完了。クローズ。 |
| **Cancelled** | 対応不要と判断されてキャンセルされた Issue。理由をコメントに記載すること。 |

### ステート遷移ルール

```
Backlog → Triage → Todo → In Progress → In Review → Testing → Done
                                                              ↘ Cancelled (任意のステートから遷移可能)
```

- **Backlog → Triage**: トリアージセッションで取り上げた時点で移行する。
- **Triage → Todo**: 優先度・担当者・スプリントが確定した時点で移行する。
- **Triage → Backlog**: 判断を保留する場合は Backlog に戻す。
- **Todo → In Progress**: 担当者が作業を開始した時点で移行する（ブランチ作成のタイミングが目安）。
- **In Progress → In Review**: PR をオープンした時点で GitHub 連携により自動移行（手動での移行も可）。
- **In Review → Testing**: PR がマージされた時点で自動移行。
- **In Review → In Progress**: レビュー指摘で追加修正が必要な場合は戻すことができる。
- **Testing → Done**: 動作確認完了・リリース後に移行する。
- **Testing → In Progress**: バグや問題が発覚した場合は戻すことができる。
- **任意 → Cancelled**: 対応不要・重複・方針変更の場合。必ずキャンセル理由をコメントに残す。

## 3. ラベル設計

### 3.1 type ラベル（Issue の種類）

| ラベル | 説明 |
|---|---|
| `type:feature` | 新機能の開発 |
| `type:bug` | 不具合・バグの修正 |
| `type:investigation` | 調査・スパイク・技術検証 |
| `type:improvement` | 既存機能の改善・最適化 |
| `type:docs` | ドキュメント作成・更新 |
| `type:security` | セキュリティ対応 |
| `type:chore` | リファクタリング・依存ライブラリ更新・設定変更など |

### 3.2 priority ラベル（優先度）

Linear 組み込みの優先度機能を使用する（ラベルではなく Priority フィールドで設定）。

| 優先度 | 説明 |
|---|---|
| **Urgent** | 緊急対応が必要。詳細は「4. 優先度ガイドライン」を参照。 |
| **High** | 高優先度。 |
| **Medium** | 中優先度。 |
| **Low** | 低優先度。 |
| **No priority** | 未トリアージ。 |

### 3.3 area ラベル（領域）

| ラベル | 説明 |
|---|---|
| `area:frontend` | UI・フロントエンド関連 |
| `area:backend` | API・バックエンドロジック関連 |
| `area:infrastructure` | インフラ・CI/CD・デプロイ関連 |
| `area:data` | データベース・データパイプライン・分析関連 |
| `area:security` | セキュリティ設計・脆弱性対応関連 |
| `area:docs` | ドキュメント・仕様書関連 |

### 3.4 status ラベル（ブロッカー・待ち状態）

| ラベル | 説明 |
|---|---|
| `status:blocked` | 他 Issue や外部要因によりブロックされている。コメントに理由を記載すること。 |
| `status:needs-info` | 情報・仕様が不足しており、確認待ち。 |
| `status:waiting-external` | 外部ベンダー・他チームの対応待ち。 |

### ラベル運用ルール

- `type:*` は必須。1 Issue に 1 つ付与する。
- `area:*` は必須。複数領域にまたがる場合は複数付与可。
- `status:*` は該当する場合のみ付与する。解消後は必ず外す。
- Priority は Linear の Priority フィールドを使用し、`type:*` ラベルと組み合わせて運用する。

## 4. 優先度ガイドライン

### Urgent（緊急）

対象:
- 本番環境でユーザー向けサービスが停止・重大な障害が発生している
- クリティカルなセキュリティ脆弱性（データ漏洩リスクや認証バイパスなど）が確認された

対応:
- 即日対応を原則とする。担当者をアサインし、Slack 等で即時エスカレーション。
- スプリント外でも着手する。

### High（高）

対象:
- 多くのユーザーに影響するバグや、スプリント内完了が求められる重要機能
- 期限が明確に設定されているタスク

対応:
- 現スプリント内での完了を目標とする。
- 翌日以内に担当者をアサインする。

### Medium（中）

対象:
- 重要だが緊急性は低い計画済みの作業
- 特定のユーザーには影響するが広範ではないバグ

対応:
- スプリント計画時に優先的にアサインを検討する。
- 2 スプリント以内での対応を目標とする。

### Low（低）

対象:
- あると嬉しい機能（nice to have）
- 技術的負債の解消・軽微なリファクタリング

対応:
- スプリントに余裕がある場合に組み込む。
- 明確な期限は設けない。

### No priority（未設定）

対象:
- まだトリアージされていない Backlog の Issue

対応:
- トリアージセッションで優先度を設定する。
- 長期間 No priority のままの Issue は定期的に見直す。

## 5. プロジェクト構成

### 5.1 スプリントプロジェクト（2 週間サイクル）

- **命名規則**: `Sprint YYYY-MM-DD`（スプリント開始日）
  - 例: `Sprint 2026-06-15`
- **期間**: 2 週間
- **作成タイミング**: 前スプリント終了の 2〜3 日前にスプリント計画ミーティングで作成
- **含める Issue**: Todo ステートで担当者がアサインされた Issue

### 5.2 マイルストーンプロジェクト（四半期目標）

- **命名規則**: `Q[1-4] YYYY Milestone: <テーマ名>`
  - 例: `Q3 2026 Milestone: ユーザー認証基盤リニューアル`
- **期間**: 四半期（3 ヶ月）
- **目的**: 複数スプリントにまたがる大きな目標・エピックの管理
- **作成タイミング**: 四半期初めの計画ミーティングで作成

### 5.3 メンテナンスプロジェクト（継続運用）

- **プロジェクト名**: `Maintenance`
- **目的**: 継続的なメンテナンス作業（依存ライブラリ更新、監視設定、ドキュメント整備など）を集約
- **運用**: クローズせず常に存在するプロジェクト。スプリントごとに一定のキャパシティを割り当てる。

### 5.4 プロジェクトテンプレート

#### スプリントプロジェクト テンプレート

```
プロジェクト名: Sprint YYYY-MM-DD
説明: [スプリントゴールを記載]
ステータス: In Progress
期間: YYYY-MM-DD 〜 YYYY-MM-DD (2 週間)
---
チェックリスト（スプリント開始時）:
- [ ] スプリントゴールを設定した
- [ ] 全 Issue に担当者をアサインした
- [ ] 全 Issue に Priority を設定した
- [ ] チームのキャパシティを確認した
```

#### マイルストーンプロジェクト テンプレート

```
プロジェクト名: Q[X] YYYY Milestone: <テーマ>
説明:
  - 目的:
  - 完了の定義 (Definition of Done):
  - 関係するステークホルダー:
ステータス: Planned / In Progress / Completed
期間: YYYY-MM-DD 〜 YYYY-MM-DD (3 ヶ月)
```

## 6. スプリント運用

### 6.1 スプリント計画

**タイミング**: スプリント開始日の前営業日（通常金曜日）
**参加者**: 全チームメンバー
**所要時間**: 60〜90 分

**手順**:

1. 前スプリントの未完了 Issue を確認し、次スプリントに持ち越すか Backlog に戻すか判断する
2. Backlog・Triage ステートの Issue をトリアージし、優先度を確定する
3. 各メンバーのキャパシティ（稼働日数）を確認する
4. 優先度の高い順に Issue をスプリントプロジェクトに追加し、担当者をアサインする
5. スプリントゴールを設定し、プロジェクト説明に記載する
6. 新しいスプリントプロジェクト（`Sprint YYYY-MM-DD`）を作成する

### 6.2 デイリースタンドアップ チェックリスト

**タイミング**: 毎営業日（非同期 or 同期。チームで決定）
**所要時間**: 15 分以内

各メンバーが確認・共有する内容:

- [ ] 昨日完了したこと
- [ ] 今日取り組む Issue（Linear の Issue ID を明記）
- [ ] ブロッカー・懸念事項（`status:blocked` や `status:needs-info` ラベルを付与しているか確認）
- [ ] スプリント目標に対する進捗の懸念はないか

ファシリテーター（週次ローテーション）が確認する内容:

- [ ] In Progress のまま長期間動いていない Issue がないか
- [ ] In Review のまま放置されている PR がないか
- [ ] `status:blocked` の Issue のブロッカーが解消されているか

### 6.3 スプリントレビューと振り返り

**タイミング**: スプリント最終日
**参加者**: 全チームメンバー
**所要時間**: 60 分（レビュー 30 分 + 振り返り 30 分）

**スプリントレビュー**:

1. Done になった Issue を確認し、デモ・成果物を共有する
2. Done にならなかった Issue の理由を確認する
3. スプリントゴールの達成度を評価する

**振り返り（レトロスペクティブ）**:

Keep / Problem / Try のフォーマットで実施:
- **Keep**: 続けるべき良かったこと
- **Problem**: 問題・改善が必要なこと
- **Try**: 次スプリントで試すアクション

アクションアイテムは `type:chore` の Issue として起票し、次スプリントに組み込む。

### 6.4 ベロシティトラッキング

- 各 Issue に **Estimate（ストーリーポイントまたは時間）** を設定する
- スプリント終了時に Done になった Issue の合計ポイントをベロシティとして記録する
- Linear の「Insights」機能でスプリントごとのベロシティを確認する
- 3〜5 スプリントの平均ベロシティをスプリント計画時のキャパシティ見積もりに活用する

## 7. GitHub 連携

### 7.1 Linear Issue と GitHub PR/コミットの紐付け

Linear の GitHub インテグレーションを有効化することで、以下の自動連携が可能になる。

**PR での紐付け方法**:
- PR タイトルまたは本文に `LINEAR-123` 形式の Issue ID を含める
- Linear サイドバーから直接 PR を作成すると自動で紐付けられる

**コミットでの紐付け方法**:
- コミットメッセージに `LINEAR-123` を含める（後述のコミットメッセージフォーマットを参照）

### 7.2 ブランチ命名規則

```
<type>/<linear-id>-<short-description>
```

- `<type>`: `feat` / `fix` / `chore` / `docs` / `refactor` / `test` のいずれか
- `<linear-id>`: Linear の Issue ID（例: `WORK-123`）
- `<short-description>`: 内容を表す簡潔な英語（ケバブケース）

**例**:
```
feat/WORK-123-user-authentication
fix/WORK-456-login-redirect-bug
chore/WORK-789-update-dependencies
```

> Linear の「Create Branch」機能を使うと、上記フォーマットに沿ったブランチ名が自動生成される。

### 7.3 GitHub 連携による自動ステート更新

GitHub インテグレーションを設定することで、以下の自動ステート変更が行われる。

| GitHub イベント | Linear ステート変更 |
|---|---|
| ブランチが作成された | Backlog/Todo → **In Progress** |
| PR がオープンされた | In Progress → **In Review** |
| PR がマージされた | In Review → **Testing** |
| PR がクローズされた（マージなし） | 変更なし（手動で対応） |

> 自動変更のタイミングや条件は Linear の設定画面（Settings > Integrations > GitHub）で調整可能。

### 7.4 コミットメッセージフォーマット

[Conventional Commits](https://www.conventionalcommits.org/) に準拠し、Linear の Issue ID を含める。

```
<type>(<linear-id>): <description>

[optional body]

[optional footer]
```

**フォーマット要素**:
- `<type>`: `feat` / `fix` / `chore` / `docs` / `refactor` / `test` / `perf`
- `<linear-id>`: Linear の Issue ID（例: `LINEAR-123`）
- `<description>`: 変更内容の簡潔な説明（英語、命令形、先頭小文字）

**例**:
```
feat(WORK-123): add OAuth2 login with Google

Implement Google OAuth2 authentication flow.
Closes WORK-123.
```

```
fix(WORK-456): correct redirect URL after login
```

```
chore(WORK-789): update axios to v1.7.0
```

**ルール**:
- `description` は 72 文字以内
- `Closes WORK-XXX` をフッターに書くと、PR マージ時に Issue が自動で Done になる
- 破壊的変更がある場合は `BREAKING CHANGE:` をフッターに記載する

## 8. トリアージプロセス

### 8.1 担当者

| 役割 | 担当 |
|---|---|
| **トリアージオーナー** | プロジェクトリード（またはその週の当番制） |
| **参加者** | 関連する担当者（任意参加） |

### 8.2 実施頻度とタイミング

| セッション | タイミング | 所要時間 |
|---|---|---|
| **定期トリアージ** | 週 1 回（月曜日推奨） | 30 分 |
| **緊急トリアージ** | Urgent Issue が起票された場合、即時 | 随時 |

### 8.3 トリアージ手順

1. **Backlog ステートの Issue を一覧表示する**
   - Linear でフィルタ: ステート = Backlog、Priority = No priority の順に並べる

2. **各 Issue に対して以下を判断する**
   - **優先度の設定**: Urgent / High / Medium / Low のいずれかを設定する
   - **type ラベルの付与**: `type:feature` / `type:bug` 等を付与する
   - **area ラベルの付与**: `area:frontend` 等を付与する
   - **担当者のアサイン**: 担当者が明確な場合は即座にアサインする
   - **スプリントへの追加**: 次スプリントに組み込む場合は Todo ステートに変更し、スプリントプロジェクトに追加する
   - **クローズの判断**: 不要・重複の場合は Cancelled に変更し、理由をコメントに残す

3. **トリアージ完了の Issue は Backlog → Todo または Cancelled へ移行する**
   - Backlog に残す場合は、次回トリアージまでの保留理由をコメントする

### 8.4 トリアージのガイドライン

- 1 Issue のトリアージは 5 分以内を目標とする。長時間の議論は別途ミーティングを設ける。
- `status:needs-info` が付いている Issue は、情報提供者をメンションしてコメントする。
- Urgent Issue は定期トリアージを待たず即時対応する。
- 30 日以上更新のない Backlog Issue は、Cancelled にするか優先度を見直す。
