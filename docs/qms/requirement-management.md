# 要件管理プロセス

## 1. 概要

### 目的

本ドキュメントは、WORK チームにおける要件の捕捉・記録・追跡・変更管理のプロセスを定義する。要件管理の目的は以下の通りである。

- 開発対象の「何を作るか」を明確にし、チーム全員が共通認識を持つ
- 要件から実装・テストまでのトレーサビリティを維持し、品質の抜け漏れを防ぐ
- 要件変更による手戻りを最小化し、影響範囲を適切に管理する

### 適用範囲

- 新機能開発（`type:feature`）
- 既存機能の重要な改善（`type:improvement`）
- 破壊的変更を伴う技術的対応
- 除外：軽微なバグ修正、ドキュメント更新、依存ライブラリ更新

---

## 2. 要件の捕捉

### 2.1 インプットソース

要件は以下のソースから発生する。各ソースに応じた初期対応を行う。

| インプットソース | 例 | 初期対応 |
|---------------|-----|---------|
| ユーザーフィードバック | サポート問い合わせ、NPS コメント | PM がトリアージし、要件チケットを起票 |
| ビジネス要求 | 経営判断、市場機会 | CTO/PM が合意の上、チケットを起票 |
| 技術的改善提案 | Tech Lead や Developer からの提案 | 技術的背景を添えてチケットを起票 |
| 法令・セキュリティ要求 | コンプライアンス要件、脆弱性対応 | Security または CTO が起票、高優先度で対応 |
| スプリントバックログ精査 | トリアージセッション中の発見 | その場で要件を整理してチケットを更新 |

### 2.2 要件の捕捉手順

1. **Slack / ミーティングで要件の芽を検知する**
   - 誰でも気づいた時点で Linear に Backlog ステートのチケットを起票する
   - この時点では詳細が不完全でも構わない（`status:needs-info` ラベルを付与）

2. **PM が要件チケットを完成させる**
   - 後述の「Feature テンプレート」に従い全フィールドを埋める
   - 不明点はステークホルダーにヒアリングし、チケットに記録する

3. **トリアージセッションで優先度を確定する**
   - 週次トリアージで優先度・担当者・スプリントへの割り当てを決定する

## 3. 要件属性

すべての要件チケットは以下の属性を持つ。Linear の Issue フィールドとテンプレートコメントを活用して管理する。

### 3.1 必須属性

| 属性 | Linear での管理方法 | 説明 |
|-----|-------------------|------|
| **ID** | Linear Issue ID（例: `WORK-123`） | 自動採番。トレーサビリティの基点となる |
| **タイトル** | Issue タイトル | 「[対象] が [目的] できる」形式を推奨 |
| **優先度** | Priority フィールド（Urgent/High/Medium/Low） | 優先度ガイドライン（linear-operations.md 参照）に従う |
| **受け入れ基準** | Issue 説明の Acceptance Criteria セクション | テスト可能な具体的条件を箇条書きで記載 |
| **ステークホルダー** | Issue 説明の Stakeholders セクション | 要件のオーナー（PM）と主要な利害関係者を明記 |
| **担当者** | Assignee フィールド | 実装担当 Developer を設定 |
| **ラベル** | Labels フィールド | `type:feature` + `area:*` を必須付与 |

### 3.2 任意属性（該当する場合は必須）

| 属性 | Linear での管理方法 | 適用条件 |
|-----|-------------------|---------|
| **依存関係** | Blocks / Blocked by リレーション | 他 Issue との依存がある場合 |
| **マイルストーン** | Project への紐付け | 四半期マイルストーンに属する場合 |
| **リリース期限** | Due Date フィールド | 外部要因による期限がある場合 |
| **見積もり** | Estimate フィールド | スプリントへの組み込み時に設定 |
| **リスクレベル** | `risk:low` / `risk:medium` / `risk:high` ラベル | リスクレビュー後に設定 |

## 4. Linear Feature テンプレート

新機能要件のチケット説明には以下のテンプレートを使用する。Linear の Issue テンプレート機能に登録して運用する。

```markdown
## 概要
<!-- この要件が解決する課題や実現したい価値を 2〜3 文で説明する -->

## ユーザーストーリー
<!-- As a [ユーザー種別], I want to [目標・行動], so that [価値・理由] -->
As a ○○ユーザー, I want to ○○できる, so that ○○できる。

## 受け入れ基準 (Acceptance Criteria)
<!-- テスト可能な条件を箇条書きで列挙する。Given/When/Then 形式を推奨 -->
- [ ] Given ○○の状態で、When ○○を行ったとき、Then ○○となること
- [ ] ○○の場合は○○のエラーが表示されること
- [ ] ○○権限のないユーザーは○○できないこと

## スコープ外 (Out of Scope)
<!-- 意図的に含めない内容を明示し、後の仕様拡張議論を防ぐ -->
- ○○は今回の対象外とする

## ステークホルダー (Stakeholders)
- **要件オーナー (PM)**: @○○
- **技術判断者 (Tech Lead)**: @○○
- **依頼元 / 最終承認者**: ○○

## 関連情報
<!-- 仕様書リンク、ユーザーインタビュー記録、競合調査等 -->
- Notion: [設計ドキュメントリンク]
- 参考 Issue: WORK-XXX

## 設計メモ（Tech Lead 記入）
<!-- 要件レビュー後に技術的な実現方針・注意点を記入する -->

## テストケース参照
<!-- テスト管理との紐付け（テスト計画作成後に記入） -->
- テストケース ID: TC-XXX
```

## 5. 要件レビューと承認プロセス

### 5.1 レビューのゲート構造

要件チケットは以下のゲートを順番に通過して初めて実装フェーズへ進む。

```
起票（Backlog）
    │
    ▼
【ゲート 1】PM 確認
    ├─ 要件テンプレート全項目の記入完了
    ├─ 受け入れ基準が具体的・テスト可能
    └─ ステークホルダーの合意取得
    │
    ▼
【ゲート 2】Tech Lead 技術レビュー
    ├─ 技術的実現可能性の確認
    ├─ 工数・複雑度の見積もり
    ├─ 依存関係・影響範囲の確認
    └─ 設計メモの記入
    │
    ▼
【ゲート 3】リスクレビュー（高リスク案件は CTO 承認）
    ├─ セキュリティリスク評価
    └─ リスクラベルの付与
    │
    ▼
Todo ステートへ移行 → スプリント計画でアサイン → In Progress
```

### 5.2 承認の記録方法

- **PM 確認完了**: Issue コメントに「要件確認完了 @Tech Lead レビューお願いします」と記載
- **Tech Lead 承認**: Issue コメントに「技術レビュー承認。設計メモを追記しました」と記載し、Issue ステートを `Todo` に変更
- **リスクレビュー承認**: Issue コメントにリスク評価結果を記載し、`risk:*` ラベルを付与

### 5.3 承認 SLA

| ゲート | SLA | 対応者 |
|--------|-----|--------|
| PM 確認 | 起票後 2 営業日以内 | PM |
| Tech Lead レビュー | PM 確認完了後 2 営業日以内 | Tech Lead |
| リスクレビュー（低リスク） | Tech Lead レビュー後 1 営業日以内 | Security |
| リスクレビュー（高リスク・CTO 承認） | Tech Lead レビュー後 3 営業日以内 | CTO |

## 6. トレーサビリティマトリクス

### 6.1 概念

トレーサビリティマトリクスとは、要件（WORK-XXX）から実装（PR・コミット）・テスト（テストケース）を一対多で紐付け、「この要件は実装されたか」「テストされたか」を追跡できる仕組みである。

```
要件 (Linear Issue)
    │
    ├─ 実装 (GitHub PR)
    │       └─ コミット (`feat(WORK-123): ...`)
    │
    └─ テスト
            ├─ ユニットテスト (`describe('WORK-123', ...)`)
            ├─ E2Eテスト（テストケース TC-123）
            └─ 手動受け入れテスト（Linear コメントに結果記録）
```

### 6.2 紐付け方法

**要件 → 実装**

- ブランチ名に Issue ID を含める: `feat/WORK-123-feature-name`
- コミットメッセージに Issue ID を含める: `feat(WORK-123): add feature`
- PR 本文に `Closes WORK-123` を記載する（マージ時に自動クローズ）

**要件 → テスト**

- ユニットテストのテストスイート名に Issue ID を含める:
  ```typescript
  describe('WORK-123: ユーザープロフィール更新', () => {
    it('正常なデータで更新できること', () => { ... })
    it('不正なメールアドレスでエラーになること', () => { ... })
  })
  ```
- テストケース文書（Notion）に `WORK-XXX` を明記し、Linear Issue からリンクを貼る
- テスト実施結果は Linear Issue のコメントに記録する

### 6.3 トレーサビリティの確認チェックリスト

リリース前に以下を確認する。

- [ ] スプリント内の全 `type:feature` チケットに対応する PR が存在する
- [ ] 各 PR に対してレビュー承認が記録されている
- [ ] 受け入れ基準の全項目に対応するテストケースが存在する
- [ ] テスト実施結果が Issue コメントまたはテスト管理ツールに記録されている

## 7. 要件変更管理（Change Request）

### 7.1 変更の種類と対応方針

実装中または実装後に要件が変更される場合がある。変更の影響範囲に応じて対応を分ける。

| 変更の種類 | 定義 | 対応方針 |
|-----------|------|---------|
| **軽微な明確化** | 曖昧だった要件を具体化する（スコープ変更なし） | Issue コメントに追記。再承認不要 |
| **スコープの縮小** | 当初要件の一部を今回対象外とする | Issue コメントに理由と今後の対応方針を記載。PM 承認 |
| **スコープの拡大** | 当初要件に新たな機能・条件を追加する | 新たな Issue を起票し、要件レビュープロセスを最初から実施 |
| **仕様の変更** | 受け入れ基準の変更・削除・置き換え | PM + Tech Lead の再承認必須。テストケースも更新 |

### 7.2 変更要求の提出フォーマット

要件変更を提案する際は、Issue コメントに以下の形式で記載する。

```markdown
## 変更要求

**変更理由**:
○○の理由により、仕様を変更したい。

**変更前**:
受け入れ基準「○○のとき○○となること」

**変更後**:
受け入れ基準「○○のとき○○となること」

**影響範囲**:
- 影響するテストケース: TC-XXX
- 影響する他の Issue: WORK-XXX
- 工数への影響: 約 ○ 時間の増減

**承認依頼**: @PM @Tech Lead
```

### 7.3 変更管理の原則

- **変更はすべて記録する**: 口頭での仕様変更は禁止。必ず Issue コメントに残す
- **影響範囲を事前に評価する**: テスト・設計・他機能への影響を確認してから承認する
- **スプリント中の大規模変更は原則禁止**: スコープ拡大はバックログへ追加し、次スプリントで対処する
- **変更履歴は Issue の変更ログ（Linear Activity）で自動記録される**

## 8. テンプレートと記入例

### 8.1 記入例：ユーザー認証機能

```markdown
## 概要
新規ユーザーが Google アカウントを使ってサービスにログインできるようにする。
現在はメール/パスワードのみ対応しており、登録の摩擦を減らすことが目的。

## ユーザーストーリー
As a 新規ユーザー, I want to Google アカウントで 1 クリックでログインできる,
so that パスワードを覚える手間なくサービスを利用開始できる。

## 受け入れ基準 (Acceptance Criteria)
- [ ] Given ログイン画面で、When「Google でログイン」ボタンをクリックしたとき、
      Then Google の OAuth2 認証画面にリダイレクトされること
- [ ] Given Google 認証完了後、Then ユーザー情報（名前・メール）が自動取得され、
      アカウントが作成されること（初回のみ）
- [ ] Given 既存メール/パスワードアカウントと同じメールアドレスで Google 認証したとき、
      Then 既存アカウントに自動でリンクされること
- [ ] Given Google 認証に失敗したとき、Then エラーメッセージが表示され、
      メール/パスワードログインにフォールバックできること
- [ ] Google アカウントの連携解除が設定画面から行えること

## スコープ外 (Out of Scope)
- Apple ID、GitHub 等その他の OAuth プロバイダー対応は今回の対象外
- 既存メール/パスワードログインの廃止は対象外

## ステークホルダー (Stakeholders)
- **要件オーナー (PM)**: @pm-name
- **技術判断者 (Tech Lead)**: @tech-lead-name
- **依頼元**: マーケティング部（ユーザー獲得改善施策）

## 関連情報
- Notion 設計書: [Google OAuth2 実装設計](https://notion.so/...)
- 参考実装: WORK-98（既存セッション管理実装）
```

## 9. 要件管理チェックリスト

### 起票時チェックリスト

- [ ] Feature テンプレートの全必須項目を記入した
- [ ] 受け入れ基準が具体的でテスト可能な形式になっている
- [ ] スコープ外を明示した
- [ ] ステークホルダーを特定し、`type:feature` ラベルを付与した

### 要件レビュー完了チェックリスト

- [ ] PM が内容を確認・承認した（コメントに記録）
- [ ] Tech Lead が技術レビューを実施し、設計メモを記入した
- [ ] リスクレビューが完了し、`risk:*` ラベルが付与されている
- [ ] Issue ステートが `Todo` に変更されている

### リリース前チェックリスト

- [ ] 全受け入れ基準に対応するテストケースが存在する
- [ ] テスト実施結果が記録されている
- [ ] 要件変更があった場合、変更内容が Issue コメントに記録されている
- [ ] `Closes WORK-XXX` が PR に記載されており、マージ後に自動クローズされる
