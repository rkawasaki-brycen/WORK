# テスト管理プロセス

## 1. 概要

### 目的

本ドキュメントは、WORK チームにおけるテスト計画・実行・欠陥管理・メトリクス計測・CI/CD 統合のプロセスを定義する。テスト活動の目的は以下の通りである。

- 製品が要件（受け入れ基準）を満たしていることを検証する
- 欠陥を本番流出前に早期発見し、手戻りコストを最小化する
- 継続的デリバリーを支える自動テストの安定した実行を維持する
- テスト結果に基づいたデータドリブンな品質改善を推進する

### スコープ

本プロセスはすべての機能開発・改善・バグ修正に適用される。テストレベルの選択は変更内容に応じて柔軟に決定する。

---

## 2. テストレベル定義

### 2.1 テストレベルの全体像

```
      ▲ 実行コスト・時間
      │
      │  ┌─────────────────────────┐
      │  │   E2E テスト             │  ← 少数・クリティカルパスのみ
      │  │   (Playwright)           │
      │  ├─────────────────────────┤
      │  │   統合テスト              │  ← API・DB レベルの組み合わせ
      │  │   (Jest / Vitest)        │
      │  ├─────────────────────────┤
      │  │   ユニットテスト          │  ← 大多数。高速・独立
      │  │   (Jest / Vitest)        │
      └──┴─────────────────────────┘
             テスト数・カバレッジ ▶
```

### 2.2 各テストレベルの詳細

#### ユニットテスト

| 項目 | 内容 |
|------|------|
| **目的** | 個々の関数・クラス・コンポーネントが単独で正しく動作することを検証 |
| **実施者** | Developer（実装と同時に作成） |
| **ツール** | Jest / Vitest（バックエンド/フロントエンドで統一） |
| **実行タイミング** | ローカル開発時（watch モード）、CI（PR 作成時） |
| **カバレッジ目標** | ラインカバレッジ 80% 以上 |
| **モック方針** | 外部依存（DB、外部 API、ファイルシステム）はモック化する |
| **速度目標** | 全スイートが 5 分以内で完了 |

**テスト命名規約**

```typescript
// 形式: describe で機能/クラスを宣言し、it で「何をすると何になるか」を記述
describe('UserService.updateProfile', () => {
  it('有効なデータを渡したとき、プロフィールが更新されること', async () => { ... })
  it('存在しないユーザーIDを渡したとき、NotFoundError がスローされること', async () => { ... })
  it('メールアドレスが重複しているとき、ConflictError がスローされること', async () => { ... })
})

// Linear Issue との紐付けが必要な場合
describe('WORK-123: Google OAuth2 ログイン', () => {
  it('有効なIDトークンで認証が成功すること', async () => { ... })
})
```

**ユニットテスト作成チェックリスト**

- [ ] 正常系（ハッピーパス）のテストが存在する
- [ ] 異常系（エラー、例外）のテストが存在する
- [ ] 境界値（空文字、null、最大値、最小値）のテストが存在する
- [ ] テストが他のテストに依存せず独立して実行できる
- [ ] テスト名が「何をテストしているか」を明確に表している

---

#### 統合テスト

| 項目 | 内容 |
|------|------|
| **目的** | 複数のコンポーネント・モジュール・サービスが連携して正しく動作することを検証 |
| **実施者** | Developer |
| **ツール** | Jest / Vitest + Supertest（API）、TestContainers（DB 統合） |
| **実行タイミング** | CI（PR 作成時）、ローカルでも実行可能 |
| **カバレッジ目標** | 主要な API エンドポイントおよびビジネスロジックフローを網羅 |
| **テスト DB** | テスト用 DB インスタンスを使用（本番・ステージング DB には接続しない） |
| **速度目標** | 全スイートが 15 分以内で完了 |

**統合テストの対象**

- REST API エンドポイント（認証・認可を含む）
- DB との CRUD 操作（マイグレーション後のスキーマ検証を含む）
- 外部サービスとの統合（モックサーバーまたはサンドボックス環境を使用）
- キャッシュ・セッション管理のロジック

---

#### E2E テスト

| 項目 | 内容 |
|------|------|
| **目的** | ユーザーの視点で、実際のブラウザを通じたシナリオが動作することを検証 |
| **実施者** | QA（テストケース設計・実行）、Developer（自動化実装サポート） |
| **ツール** | Playwright |
| **実行タイミング** | ステージング環境へのデプロイ後（PR マージ後の CI パイプラインで自動実行） |
| **対象範囲** | クリティカルユーザージャーニー（最重要フローのみ）|
| **速度目標** | 主要スイートが 20 分以内で完了（並列実行を活用） |

**E2E テストの対象選定基準**

E2E テストはメンテナンスコストが高いため、以下の基準でクリティカルパスに絞る。

- ビジネスに直結する最重要フロー（会員登録、ログイン、購入フロー等）
- 頻繁に使用され、かつ不具合時の影響が大きい機能
- 複数のサービス・ページをまたぐ複雑なユーザー操作
- **除外**: 全ての UI パターン、細かいバリデーションメッセージ（ユニットテストで対応）

---

#### セキュリティテスト

| 項目 | 内容 |
|------|------|
| **目的** | セキュリティ脆弱性・設定ミスを検出する |
| **実施者** | Security（自動スキャン + 手動レビュー）|
| **ツール** | CodeQL（静的解析）、Snyk（依存関係）、OWASP ZAP（動的スキャン・必要時）|
| **実行タイミング** | CI（PR 作成時: 自動スキャン）、四半期ごと（手動ペネトレーションテスト）|
| **結果の管理** | GitHub Security タブ / Snyk ダッシュボード |

---

#### パフォーマンステスト

| 項目 | 内容 |
|------|------|
| **目的** | 負荷・ストレス条件下でのシステム性能を検証する |
| **実施者** | QA + Developer |
| **ツール** | k6（負荷テスト）、Lighthouse CI（フロントエンドパフォーマンス）|
| **実行タイミング** | 大規模機能リリース前・パフォーマンス改善施策後（必要時） |
| **指標目標** | API 応答時間 P95 < 500ms、Lighthouse スコア > 80 |

## 3. テスト計画

### 3.1 テスト計画の策定タイミング

テスト計画は要件レビュー承認後・実装開始前に QA が主導して策定する。

```
要件承認（WORK-XXX: Todo ステート）
    │
    ▼
QA がテスト計画を立案（1 営業日以内）
    ├─ テスト対象範囲の決定
    ├─ テストレベルの選定
    ├─ テストケースの設計
    └─ テスト環境・データの準備方針
    │
    ▼
Tech Lead がテスト計画をレビュー
    │
    ▼
実装フェーズ並行でテストケース文書を完成させる
```

### 3.2 何をテストするかの判断基準

以下のリスクマトリクスを参考に、テストの優先度と深度を決定する。

| 機能の重要度 | 変更の影響範囲 | テスト深度 |
|------------|-------------|-----------|
| 高（コア機能・収益直結） | 広範囲 | ユニット + 統合 + E2E + セキュリティ |
| 高 | 限定的 | ユニット + 統合 + セキュリティ |
| 中 | 広範囲 | ユニット + 統合 |
| 中 | 限定的 | ユニット |
| 低（軽微な UI 修正等） | 限定的 | ユニット（最小限）|

### 3.3 テストカバレッジ方針

| テストレベル | カバレッジ指標 | 目標値 | 下限（CI ブロック閾値） |
|------------|-------------|--------|---------------------|
| ユニットテスト | ラインカバレッジ | 80% | 75% |
| 統合テスト | 主要 API エンドポイント網羅率 | 90% | - |
| E2E テスト | クリティカルユーザージャーニー網羅率 | 100% | - |

カバレッジは手段であり目的ではない。カバレッジ数値を満たすためだけのテストより、意味のあるテストを優先する。

### 3.4 テストデータ管理

| データ種別 | 管理方針 |
|-----------|---------|
| ユニット / 統合テスト用データ | テストコード内にフィクスチャとして定義。`tests/fixtures/` に集約 |
| E2E テスト用データ | シードスクリプトでテスト用 DB に投入。テスト後にクリーンアップ |
| 本番データの利用 | 禁止。必要な場合は個人情報を匿名化・マスキング処理した後に使用 |

## 4. テスト実行と報告

### 4.1 テスト実行環境

| 環境 | 用途 | デプロイ条件 |
|------|------|------------|
| ローカル開発環境 | Developer のユニット・統合テスト実行 | 開発者が任意に実行 |
| CI 環境（GitHub Actions） | PR 作成時の自動テスト実行 | PR 作成・更新時に自動トリガー |
| ステージング環境 | QA による E2E・手動受け入れテスト | PR マージ後に自動デプロイ |
| 本番環境 | スモークテスト（デプロイ後の最小確認） | リリースデプロイ後に自動実行 |

### 4.2 テスト実行の報告

**CI 自動テスト**

- GitHub Actions のサマリーに結果を自動表示する
- テストカバレッジレポートは PR コメントに自動投稿する（`jest-coverage-report` アクション等を利用）
- 失敗したテストケースは GitHub Actions のログで詳細を確認できる

**QA 手動テスト結果**

- テスト実施後、Linear Issue にコメントで結果を報告する
- 報告フォーマット:

```markdown
## QA テスト実施結果

**実施日時**: YYYY-MM-DD HH:MM
**実施者**: @qa-name
**テスト環境**: ステージング (https://staging.example.com)
**ビルドバージョン**: v1.4.0-rc.1

### 結果サマリー

| テストケース | 結果 | 備考 |
|------------|------|------|
| TC-001 Google ログイン正常フロー | ✅ PASS | |
| TC-002 既存アカウントとのリンク | ✅ PASS | |
| TC-003 Google 認証失敗時のエラー表示 | ❌ FAIL | バグ WORK-456 として起票 |

**総合判定**: NG（WORK-456 の修正後に再テストが必要）
```

### 4.3 リリース判定基準

以下の条件をすべて満たした場合にのみリリース承認を与える。

- [ ] ユニットテストが全件 PASS し、カバレッジが 75% 以上
- [ ] 統合テストが全件 PASS
- [ ] E2E テスト（クリティカルパス）が全件 PASS
- [ ] QA による受け入れテストで Critical / High の未解決バグがない
- [ ] セキュリティスキャンで Critical / High の未解決脆弱性がない
- [ ] ステージング環境でのスモークテストが PASS

## 5. 欠陥（バグ）管理

### 5.1 欠陥ライフサイクル

```
欠陥の検出（テスト・レビュー・本番モニタリング）
    │
    ▼
Linear に `type:bug` チケットを起票（検出者）
    │
    ▼
【トリアージ】重大度・優先度を設定（QA または PM）
    ├─ Critical: 即時エスカレーション → ホットフィックスプロセスへ
    ├─ High: 現スプリントで修正
    ├─ Medium: 当スプリント内 or 次スプリントで対応
    └─ Low: バックログに登録
    │
    ▼
担当 Developer にアサイン → 修正実装
    │
    ▼
Developer が修正 PR を作成 → コードレビュー
    │
    ▼
QA が修正確認（回帰テスト含む）
    │
    ├─ 修正確認 OK → Issue を Done にクローズ
    └─ 修正不十分 → Issue を In Progress に戻し、コメントで詳細を報告
```

### 5.2 欠陥の重大度（Severity）分類

| 重大度 | 定義 | 例 |
|--------|------|-----|
| **Critical** | サービス停止・データ破損・セキュリティ侵害・全ユーザー影響 | ログインできない、データ消失、個人情報漏洩 |
| **High** | 主要機能の動作不良・多くのユーザーに影響（回避策なし） | 決済フロー不具合、特定ページが表示されない |
| **Medium** | 機能の部分的な不具合（回避策あり）・一部ユーザーに影響 | フォームの送信後にリロードが必要、特定条件でエラー |
| **Low** | 軽微な UI の問題・誤字・軽微なデザイン崩れ | ボタンの余白が少しずれている |

### 5.3 欠陥チケット（`type:bug`）の記載フォーマット

```markdown
## バグ概要
<!-- 1 文でバグを説明する -->
○○の操作をしたとき、○○が起きるべきところ○○が発生する。

## 再現手順
1. ○○の状態でログインする
2. ○○ページに遷移する
3. ○○ボタンをクリックする
4. → 期待: ○○が表示される
5. → 実際: ○○エラーが発生する

## 期待する動作
○○であること。

## 実際の動作
○○になっている。

## 環境情報
- **環境**: ステージング / 本番
- **ブラウザ**: Chrome 124 / Safari 17
- **OS**: macOS 15
- **再現率**: 100% / 50%（条件: ○○の場合のみ）

## スクリーンショット / ログ
<!-- エラーログ、スクリーンショット、HAR ファイル等を添付 -->

## 関連 Issue
<!-- 原因と思われる PR や関連 Issue があれば記載 -->
```

### 5.4 欠陥優先度（Priority）と対応期限

| 優先度 | 対応期限 | アクション |
|--------|---------|-----------|
| **Urgent** | 即時（当日中） | Slack でエスカレーション、ホットフィックスプロセス発動 |
| **High** | 現スプリント内（リリースブロック） | 現スプリントに割り込み対応 |
| **Medium** | 当スプリント or 次スプリント | 次のトリアージセッションでスプリントに追加 |
| **Low** | 計画的に対応 | バックログに積み、余裕があるスプリントで対応 |

### 5.5 回帰テスト方針

バグ修正後は以下の回帰テストを実施する。

- **必須**: 修正した機能のユニットテスト + 統合テストを追加または更新する
- **推奨**: 修正内容に関連する E2E テストシナリオを実行する
- **目的**: 同じバグが再発しないことを自動テストで保証する

バグ修正 PR には以下を含めること。

```typescript
// バグ修正時は必ず再現するテストを追加する
describe('WORK-456: ○○バグの回帰テスト', () => {
  it('○○の条件のとき、○○が発生しないこと（修正前は発生していた）', async () => {
    // 修正前はここで失敗していたテスト
    ...
  })
})
```

## 6. テストメトリクスと KPI

### 6.1 計測する主要メトリクス

| メトリクス | 定義 | 計測方法 | 計測頻度 |
|-----------|------|---------|---------|
| **テストカバレッジ** | ラインカバレッジ（ユニットテスト） | CI レポート（Jest/Vitest） | PR ごと |
| **バグ検出フェーズ分布** | どのフェーズで欠陥を発見したか（開発中/テスト/本番） | Linear バグチケットのラベル | 月次 |
| **本番バグ流出件数** | Critical/High バグの本番流出数 | Linear + インシデント記録 | 月次 |
| **平均バグ修正リードタイム** | バグ起票からクローズまでの時間 | Linear Insights | 月次 |
| **E2E テスト安定性** | フレーキーテスト（不安定なテスト）の割合 | CI 成功率のモニタリング | 週次 |
| **テスト実行時間** | CI の全テスト実行時間 | GitHub Actions ログ | PR ごと |

### 6.2 KPI ダッシュボード

以下の KPI を月次でスプリントレビューに報告する。

```
月次品質レポート（テンプレート）
━━━━━━━━━━━━━━━━━━━━━━━
対象期間: YYYY年MM月

【テストカバレッジ】
- 現在値: XX%（目標: 80%）

【バグ指標】
- Critical バグ本番流出: X 件（目標: 0 件）
- High バグ本番流出: X 件（目標: 0 件）
- 月内起票バグ数: X 件
- 月内クローズバグ数: X 件
- 平均修正リードタイム: X.X 日

【バグ発見フェーズ分布】
- 開発中（コードレビュー前）: XX%
- コードレビュー: XX%
- テスト（QA）: XX%
- 本番: XX%

【E2E テスト安定性】
- フレーキーテスト率: X%（目標: 5% 以下）
- CI 平均実行時間: XX 分

【アクションアイテム】
- ○○ の改善を次スプリントで実施する（担当: @○○）
━━━━━━━━━━━━━━━━━━━━━━━
```

### 6.3 フレーキーテストの管理

フレーキーテスト（条件によって PASS / FAIL が変わる不安定なテスト）は開発速度を阻害する主要因であり、積極的に対処する。

| 対応 | タイミング |
|------|-----------|
| フレーキーテストを発見した場合、`test:flaky` ラベルを付けて Linear に起票する | 発見時 |
| フレーキーテストの根本原因を調査・修正する | 次スプリント内 |
| 修正が困難な場合は一時的に skip + コメントを付けて記録し、技術的負債として管理する | 判断後 |
| CI での 3 回以上の不安定な実績があるテストは自動的に調査対象とする | 週次確認 |

## 7. CI/CD 統合

### 7.1 CI パイプライン構成

```yaml
# .github/workflows/ci.yml の概要（実際のファイルは別途管理）

# PR 作成・更新時にトリガー
on:
  pull_request:
    branches: [main, develop]

jobs:
  # ジョブ 1: Lint・型チェック（最速で失敗させる）
  lint-and-typecheck:
    - ESLint
    - TypeScript コンパイル

  # ジョブ 2: ユニットテスト + カバレッジ
  unit-test:
    needs: lint-and-typecheck
    - Jest / Vitest 実行
    - カバレッジレポートを PR コメントに投稿
    - カバレッジ下限（75%）を下回った場合は CI を失敗させる

  # ジョブ 3: 統合テスト
  integration-test:
    needs: lint-and-typecheck
    - TestContainers で DB を起動
    - 統合テスト実行

  # ジョブ 4: セキュリティスキャン（並列実行）
  security-scan:
    - CodeQL 静的解析
    - Snyk 依存関係スキャン
    - GitLeaks シークレットスキャン

  # ジョブ 5: ビルド確認
  build:
    needs: [unit-test, integration-test]
    - プロダクションビルドが成功することを確認
```

### 7.2 ステージングへの CD パイプライン

```yaml
# PR マージ後にステージングへ自動デプロイ

on:
  push:
    branches: [main]

jobs:
  deploy-staging:
    - ステージング環境へデプロイ
    - スモークテスト実行（主要エンドポイントの疎通確認）
    - Playwright E2E テスト実行（クリティカルパスのみ）
    - Slack にデプロイ完了通知
    - 失敗した場合は自動ロールバック + Slack アラート
```

### 7.3 PR マージ条件（Branch Protection Rules との連携）

以下のステータスチェックが全て green になるまで main ブランチへのマージをブロックする。

| チェック名 | 必須/任意 | 失敗時の影響 |
|-----------|---------|------------|
| `ci/lint-and-typecheck` | 必須 | マージブロック |
| `ci/unit-test` | 必須 | マージブロック |
| `ci/integration-test` | 必須 | マージブロック |
| `ci/security-scan` | 必須 | Critical/High 脆弱性がある場合のみブロック |
| `ci/build` | 必須 | マージブロック |

### 7.4 テスト失敗時の対応フロー

```
CI テスト失敗
    │
    ▼
Developer が失敗原因を調査（30 分以内）
    │
    ├─ 実装バグ → 修正してプッシュ
    │
    ├─ フレーキーテスト → Linear に `test:flaky` チケットを起票し、
    │                      一時的に skip + コメントで明記してプッシュ
    │
    └─ テスト環境の問題 → Tech Lead に報告し、
                          CI の状態を Slack チャンネルに通知
```

### 7.5 テスト環境の管理

| 環境 | 管理方針 |
|------|---------|
| ユニットテスト | 環境依存を排除。モックを使用 |
| 統合テスト（DB） | Docker / TestContainers で毎回クリーンな状態から起動 |
| ステージング | インフラは `infra/` ディレクトリの IaC（Terraform 等）で管理 |
| テストデータ | シードスクリプトを `scripts/seed-test-data.ts` で管理 |

## 8. テスト活動の継続的改善

### 8.1 テスト戦略の定期見直し

| レビュー | タイミング | 主担当 | アウトカム |
|---------|-----------|--------|-----------|
| テストカバレッジ傾向の確認 | スプリントレビューごと | QA | 低カバレッジ領域の特定・改善計画 |
| E2E テストシナリオの棚卸し | 四半期ごと | QA | 陳腐化したテストの削除・新規追加 |
| テスト実行時間の最適化 | CI が 30 分を超えた場合 | Tech Lead + Developer | 並列化・テスト分割の実施 |
| フレーキーテストの撲滅 | 週次 CI レポート確認 | Developer | 根本原因修正 |

### 8.2 テストナレッジの共有

- バグの根本原因分析（RCA）結果をチームに共有し、同種のバグを未然に防ぐテストパターンを確立する
- 「発見しにくかった欠陥」は週次スタンドアップまたはレトロスペクティブで共有する
- テストのベストプラクティスは `tests/README.md` に集約し、新規メンバーのオンボーディングで活用する
