# 品質マネジメントシステム（QMS）概要

## 1. 目的とスコープ

### 目的

本 QMS（Quality Management System）は、WORK チームにおける製品開発の品質を体系的に管理し、顧客満足と継続的改善を実現するための枠組みを定義する。ISO 9001:2015 の考え方を小規模開発チーム向けに実用的に適合させたものであり、過度な官僚主義を排除しつつ、本質的な品質管理活動を確実に実施することを目指す。

### スコープ

- 対象プロセス：要件管理、設計・実装、レビュー、テスト、リリース、改善
- 対象チーム規模：5〜20 名
- 除外：インフラ構築・運用の詳細手順（別途 Runbook で定義）

### 基本方針

| 原則 | 説明 |
|------|------|
| **品質の前倒し** | 後工程での手戻りを防ぐため、各フェーズの入口で品質を担保する |
| **トレーサビリティ** | 要件から実装・テストまで一貫して追跡できる状態を維持する |
| **継続的改善** | レトロスペクティブとメトリクスに基づき、プロセスを定期的に見直す |
| **実用性優先** | ルールはチームが実際に守れる現実的な水準に設定する |

## 2. ISO 9001:2015 との対応マッピング

本 QMS は ISO 9001:2015 の主要要求事項と以下の通り対応する。認証取得を目的とするものではなく、同規格の考え方を開発プロセスに組み込むことを目的とする。

### 主要条項との対応

| ISO 9001 条項 | 要求内容の概要 | 本 QMS での対応 |
|--------------|--------------|----------------|
| **4. 組織の状況** | 内外の課題の理解、利害関係者のニーズ把握 | 要件管理プロセス（ステークホルダー特定）|
| **5. リーダーシップ** | 品質方針の設定、役割・責任・権限の明確化 | 開発ライフサイクル定義書のロール定義 |
| **6. 計画** | リスク・機会への対応、品質目標の設定 | リスクレビューフェーズ、OKR/KPI 管理 |
| **7. 支援** | 資源・力量・認識・コミュニケーション・文書化情報 | 本 docs/ 配下の各ドキュメント群 |
| **8. 運用** | 製品・サービス実現の計画と管理 | 開発ライフサイクル、各プロセスドキュメント |
| **8.3 設計・開発** | 設計・開発の計画、インプット/アウトプット、レビュー、検証、妥当性確認 | レビュー管理、テスト管理 |
| **8.4 外部提供プロセス** | 外部提供のプロセス・製品・サービスの管理 | 依存ライブラリ管理（Snyk スキャン）|
| **9. パフォーマンス評価** | 監視・測定・分析・評価、内部監査、マネジメントレビュー | テストメトリクス、スプリントレビュー |
| **10. 改善** | 不適合と是正処置、継続的改善 | バグ管理、レトロスペクティブ、ポストモーテム |

### PDCA サイクルとの対応

```
Plan（計画）
  └─ 要件管理 → 設計 → リスクレビュー → テスト計画

Do（実行）
  └─ 実装 → コードレビュー → テスト実行

Check（評価）
  └─ テスト結果確認 → メトリクス計測 → スプリントレビュー

Act（改善）
  └─ バグ修正 → レトロスペクティブ → プロセス改善
```

## 4. 品質目標（Quality Objectives）

品質目標は四半期ごとに見直し、Linear のマイルストーンプロジェクトに紐付けて管理する。以下は標準的な目標値の目安であり、チームの現状に応じて調整する。

| 指標 | 目標値 | 測定方法 | 測定頻度 |
|------|--------|---------|---------|
| テストカバレッジ（ユニット） | 80% 以上 | CI レポート | PR ごと |
| Critical/High バグの本番流出件数 | 0 件/月 | Linear バグチケット | 月次 |
| PR レビュー SLA 遵守率（24h 以内） | 90% 以上 | GitHub Insights | 週次 |
| スプリント完了率 | 80% 以上 | Linear Insights | スプリントごと |
| ホットフィックス発生頻度 | 月 1 回以下 | GitHub リリースタグ | 月次 |
| 本番インシデントの MTTR | 2 時間以内 | インシデント記録 | 発生時 |

## 5. 品質記録の管理

### 記録の保管場所

| 記録の種類 | 保管場所 | 保管期間 |
|-----------|---------|---------|
| 要件チケット | Linear | プロジェクト存続期間 |
| PRおよびコードレビュー履歴 | GitHub | 永続 |
| テスト結果レポート | GitHub Actions アーティファクト / Notion | 1 年 |
| バグチケット | Linear | プロジェクト存続期間 |
| インシデント・ポストモーテム | Notion | 永続 |
| スプリントレトロスペクティブ記録 | Notion | 2 年 |
| セキュリティスキャン結果 | GitHub Security タブ / Snyk | 1 年 |

### ドキュメントのバージョン管理

- すべての QMS ドキュメントは Git で管理し、変更履歴は GitHub のコミット履歴で追跡する
- 重大な変更（プロセスの大幅変更）は PR を通じてレビューし、Tech Lead が承認する
- 各ドキュメント末尾にバージョン履歴テーブルを設け、変更概要を記録する

## 6. 内部監査とマネジメントレビュー

### 内部監査（四半期ごと）

Tech Lead が主導し、以下の観点で QMS の実施状況を確認する。

- [ ] 各プロセスドキュメントに従って実際の開発が行われているか
- [ ] 品質目標の達成状況
- [ ] 未解決の不適合・改善アクションの進捗
- [ ] ドキュメントの最新性（陳腐化していないか）

監査結果は Notion に記録し、改善が必要な事項は Linear に `type:chore` チケットとして起票する。

### マネジメントレビュー（半期ごと）

CTO が主導し、以下を確認・判断する。

- 品質目標の達成度評価
- QMS 全体の有効性評価
- 次期の品質目標・リソース配分の決定
- プロセス・ドキュメントの重大変更の承認

## 7. 継続的改善の仕組み

### 改善インプットの収集経路

| インプット | 収集タイミング | 担当 |
|-----------|--------------|------|
| スプリントレトロスペクティブ | スプリント終了時 | 全メンバー |
| ポストモーテム（インシデント後） | インシデント解決後 24 時間以内 | Tech Lead |
| バグトレンド分析 | 月次 | QA |
| セキュリティスキャン結果の傾向 | PR ごと・月次集計 | Security |
| チームメンバーからの随時提案 | 随時 | 全メンバー |

### 改善アクションの管理

1. 改善提案を Linear に `type:chore`、`area:docs` ラベルで起票する
2. 次のスプリント計画時にトリアージし、優先度を設定する
3. 担当者をアサインして実施する
4. 完了後、該当ドキュメントのバージョン履歴を更新する
