# リリース管理プロセス

## 目的

本文書は、ソフトウェアリリースを安全かつ確実に実施するための手順を定める。リリースの計画から実施後の監視まで、一貫したプロセスを提供することで、サービスの品質と安定性を確保する。

## 適用範囲

本プロセスは本番環境へのすべてのリリースに適用する。ただし、ホットフィックス（緊急変更）については[変更管理プロセス](./change-management.md)の緊急変更フローを優先する。

---

## 1. リリース計画と スケジューリング

### 1.1 リリース種別

| リリース種別 | 頻度 | 内容 |
|---|---|---|
| 定期リリース | 週1〜2回（スプリント終了時） | 機能追加・改善・バグ修正 |
| パッチリリース | 随時 | 軽微なバグ修正・依存ライブラリの更新 |
| ホットフィックス | 緊急時 | 本番障害の緊急修正 |
| メジャーリリース | 四半期に1回程度 | 大規模な機能追加・アーキテクチャ変更 |

### 1.2 リリーススケジュールの策定

**定期リリースの場合:**
1. スプリント計画時にリリース対象のIssueを確定する
2. リリース日時を決定する（推奨: 月〜木曜の午後、金曜・祝前日は避ける）
3. Linearのマイルストーンまたはリリースタグで管理する
4. 関係者（PdM、QA、カスタマーサポート等）に2営業日前までに通知する

**メジャーリリースの場合:**
1. 2週間以上前からリリース計画を策定する
2. リハーサルデプロイ（ステージング環境での完全なリリース手順の実施）を行う
3. 必要に応じてメンテナンスウィンドウを設定・告知する

### 1.3 リリースウィンドウ

| 推奨 | 時間帯 | 理由 |
|---|---|---|
| 推奨 | 平日 11:00〜16:00 JST | トラフィックが安定、対応スタッフが揃っている |
| 避けること | 金曜・祝前日 | 問題発生時の対応が困難 |
| 避けること | 月曜朝 | ユーザーアクセス集中時間帯 |
| 避けること | 深夜 | 監視対応が困難（緊急時を除く） |

## 2. リリース準備チェックリスト

### 2.1 コード・品質確認

- [ ] すべての対象IssueがDone状態になっている
- [ ] 全テスト（ユニット、統合、E2E）がパスしている
- [ ] コードレビューがすべて完了・承認されている
- [ ] セキュリティスキャン（依存ライブラリの脆弱性等）が完了している
- [ ] リリースブランチがmainブランチと同期されている
- [ ] データベースマイグレーションスクリプトが準備されている（必要な場合）

### 2.2 ドキュメント確認

- [ ] リリースノートが作成されている
- [ ] APIの変更がドキュメントに反映されている（必要な場合）
- [ ] 環境変数・設定の変更が運用手順書に反映されている（必要な場合）
- [ ] ユーザー向けの変更通知が準備されている（必要な場合）

### 2.3 環境・インフラ確認

- [ ] ステージング環境でのテストが完了している
- [ ] 本番環境のキャパシティが確認されている
- [ ] 必要な環境変数・シークレットが設定されている
- [ ] バックアップが取得済みである（DBマイグレーションがある場合は必須）

### 2.4 運用・監視確認

- [ ] 監視アラートが設定されている（または既存のものが有効）
- [ ] ロールバック手順が明確になっている
- [ ] 担当者（実施者・承認者・オンコール）が確定している
- [ ] エスカレーション連絡先が確認されている
- [ ] リリース後の監視担当者が決まっている

## 3. Go/No-Go 判断基準

リリース実施直前に以下の基準でGo/No-Goを判断する。

### 3.1 Go基準（すべてを満たすこと）

- [ ] リリース準備チェックリストがすべて完了している
- [ ] ステージング環境での最終テストが成功している
- [ ] 必要な承認がすべて得られている
- [ ] オンコール担当者が待機可能な状態にある
- [ ] 既知の重大なブロッカーが存在しない
- [ ] ロールバック手順が準備・確認されている

### 3.2 No-Go条件（1つでも該当すればリリースを延期）

- 未解決のP0/P1バグが存在する
- テスト成功率が100%でない（重要なテストが失敗している）
- 承認が得られていない
- ロールバック手順が不明確
- 本番環境に現在アクティブなインシデントが存在する
- 主要担当者が対応不可能な状態にある
- 前回リリースからの重大なインシデントの根本原因分析が未完了

### 3.3 Go/No-Goミーティング

メジャーリリースまたは中〜高リスクの変更については、リリース実施1時間前にGo/No-Goを確認する短いミーティング（15分以内）を実施する。

## 4. リリース実施手順

### 4.1 標準的なリリース手順

```
1. リリース開始の宣言
   - Slackの #releases チャンネルにリリース開始を投稿する
   - 「[リリース開始] サービス名 vX.X.X リリース開始します」

2. 事前確認
   - 本番環境の現在の状態・エラーレートをダッシュボードで確認する
   - アクティブなインシデントがないことを確認する

3. データベースマイグレーション（必要な場合）
   - バックアップの最終確認
   - マイグレーションの実行
   - マイグレーション完了の確認

4. デプロイの実行
   - CI/CDパイプラインからデプロイをトリガーする
   - デプロイの進行をログで監視する

5. デプロイ完了確認
   - すべてのインスタンス/Podが新バージョンで起動していることを確認する
   - ヘルスチェックエンドポイントの応答を確認する

6. スモークテストの実施
   - 主要機能の動作確認（本番環境での最小限のテスト）
   - 新機能・修正内容の動作確認

7. リリース完了の宣言
   - Slackに完了を投稿する
   - 「[リリース完了] サービス名 vX.X.X リリース完了しました」

8. 監視フェーズへ移行
   - リリース後30分間の集中監視を開始する（後述）
```

### 4.2 ブルーグリーンデプロイの場合

1. グリーン環境に新バージョンをデプロイする
2. グリーン環境でのスモークテストを実施する
3. トラフィックを段階的に切り替える（10% → 50% → 100%）
4. 各ステップで5分間観察し、問題がなければ次のステップへ進む
5. 完全切り替え後30分間監視する
6. 問題がなければブルー環境を次回リリース用に保持する

---

## 5. リリース後モニタリング（30分間）

### 5.1 監視手順

リリース完了後、**最低30分間**は以下のメトリクスを積極的に監視する。

| 監視項目 | 確認頻度 | アラート閾値（例） |
|---|---|---|
| エラーレート (5xx) | 5分ごと | リリース前の2倍以上 |
| レイテンシ (P95/P99) | 5分ごと | リリース前の1.5倍以上 |
| CPU/メモリ使用率 | 5分ごと | 80%以上が続く場合 |
| アクティブユーザー数 | 10分ごと | 異常な急減 |
| キューの滞留（該当する場合） | 5分ごと | 通常の3倍以上 |
| データベース接続数/クエリ時間 | 5分ごと | 通常の2倍以上 |

### 5.2 30分間の監視スケジュール

```
T+0分  : リリース完了。監視開始をSlackに宣言する。
T+5分  : 初回確認。エラーレート、レイテンシを確認する。
T+10分 : 2回目確認。全メトリクスを確認する。
T+15分 : 3回目確認。安定していれば安定報告をSlackに投稿する。
T+30分 : 最終確認。問題なければ監視フェーズ終了をSlackに投稿する。
```

### 5.3 異常検知時の対応

- **軽微な異常（閾値未満だが増加傾向）:** 引き続き監視、5分後に再評価する
- **軽微な閾値超過（一時的な可能性）:** 担当エンジニアに通知、10分以内に収束しなければロールバックを検討する
- **重大な閾値超過または明確な機能障害:** 即時ロールバック判断を行う

---

## 6. ロールバック判断基準と手順

### 6.1 即時ロールバック基準

以下のいずれかに該当する場合、即時ロールバックを実施する:

- エラーレートがリリース前の3倍以上に上昇している
- 主要機能が完全に動作していない
- データの不整合が検出された
- セキュリティインシデントが発生した
- リリース後のスモークテストが失敗した

### 6.2 検討によるロールバック基準

以下に該当する場合、担当エンジニアとリードが協議してロールバックを判断する:

- エラーレートがリリース前の2〜3倍に上昇している
- パフォーマンスが著しく低下している（P95レイテンシが1.5倍超）
- 一部の機能に問題があるが回避策がある
- 想定外の副作用が発生しているが重大ではない

### 6.3 ロールバック手順

**コードのロールバック:**
```
1. Slackの #releases チャンネルにロールバック開始を投稿する
   「[ロールバック開始] サービス名 vX.X.X → vX.X.X (前バージョン)」

2. CI/CDパイプラインからロールバックをトリガーする
   または前のバージョンのタグ/コミットをデプロイする

3. デプロイ完了後、スモークテストを実施する

4. メトリクスが正常に戻ったことを確認する

5. ロールバック完了をSlackに投稿する
   「[ロールバック完了] 正常状態に戻りました」

6. インシデントレポートの作成を開始する
```

**データベースマイグレーションのロールバック:**
```
1. 逆方向のマイグレーションスクリプトを実行する
   （事前に準備されていることを確認）
2. データの整合性を確認する
3. アプリケーションの旧バージョンをデプロイする
4. 動作確認を実施する
```

### 6.4 ロールバック後の対応

1. インシデントとしてLinear Issueに記録する
2. 根本原因分析（RCA）を48時間以内に開始する
3. 次回リリース前に問題を修正し、テストを強化する

## 7. リリースノートテンプレート

```markdown
# リリースノート - [サービス名] v[バージョン番号]

**リリース日:** YYYY-MM-DD
**リリース担当:** [名前]

## 概要
このリリースの主な変更点を1〜3文で説明する。

## 新機能
- **[機能名]:** 機能の説明。([Linear Issue番号])
- **[機能名]:** 機能の説明。([Linear Issue番号])

## 改善・変更
- **[改善内容]:** 変更の説明。([Linear Issue番号])

## バグ修正
- **[バグ内容]:** 修正の説明。([Linear Issue番号])

## 破壊的変更 (Breaking Changes)
⚠️ 以下の変更は既存の動作に影響します:
- [変更内容と対応方法]

## 非推奨 (Deprecated)
- [非推奨になる機能と移行先]

## 既知の問題
- [既知の問題があれば記載]

## アップグレード手順
特別な対応が必要な場合のみ記載:
1. 手順1
2. 手順2

## 依存ライブラリの更新
- [ライブラリ名]: vX.X.X → vX.X.X
```

## 8. リリース後の振り返り

### 8.1 通常リリースの振り返り

- リリース後1週間以内にLinear Issueにリリースの所見を記録する
- 次のスプリントレトロスペクティブでリリースの問題点を議題に含める

### 8.2 ロールバックが発生したリリースの振り返り

- 48時間以内に根本原因分析（RCA）を実施する
- RCAレポートをNotionに記録する
- 予防策をLinear Issueとして登録し、次スプリントで対応する
