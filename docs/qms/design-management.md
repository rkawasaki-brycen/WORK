# 設計管理プロセス

## 目的

本文書は、ソフトウェア開発における設計プロセスの品質を確保するための手順を定める。設計の各フェーズにおける成果物、レビュー、承認、および変更管理の方法を規定する。

## 適用範囲

本プロセスは、新規機能開発、既存機能の大規模改修、アーキテクチャ変更を伴うすべてのプロジェクトに適用する。

---

## 1. 設計フェーズ

### 1.1 概念設計フェーズ (Conceptual Design)

**目的:** 要求事項を分析し、解決策の方向性を定める。

**主な活動:**
- ビジネス要件と技術要件の整理
- 複数の解決策候補の検討
- 技術的フィージビリティの評価
- 高レベルアーキテクチャの草案作成
- 非機能要件（性能、セキュリティ、拡張性）の確認

**成果物:**
- 要件定義書（またはLinear Issueの詳細記述）
- アーキテクチャ候補一覧
- 技術選定の根拠メモ
- 概念設計レビュー議事録

**完了基準:**
- ステークホルダーが解決策の方向性に合意している
- 主要な技術リスクが特定されている
- 概算工数・コストの見積もりが存在する

---

### 1.2 詳細設計フェーズ (Detailed Design)

**目的:** 概念設計を具体化し、実装可能な設計仕様を作成する。

**主な活動:**
- データモデル設計（ER図、スキーマ定義）
- API設計（エンドポイント、リクエスト/レスポンス仕様）
- コンポーネント間のインターフェース定義
- エラーハンドリング戦略の設計
- セキュリティ設計（認証・認可、データ保護）
- テスト戦略の策定

**成果物:**
- データモデル図
- API仕様書（OpenAPI/Swagger形式推奨）
- シーケンス図・フロー図
- セキュリティ設計書
- テスト計画書

**完了基準:**
- すべてのAPIエンドポイントが定義されている
- データモデルがレビューされ承認されている
- エラーケースが網羅されている
- セキュリティ要件が設計に反映されている

---

### 1.3 技術設計フェーズ (Technical Design)

**目的:** 実装レベルの技術詳細を確定し、開発者が迷わず実装できる状態にする。

**主な活動:**
- クラス図・モジュール構成の設計
- アルゴリズムの選定と詳細化
- 外部サービス・ライブラリの選定
- パフォーマンス設計（キャッシュ戦略、クエリ最適化）
- インフラ設計（デプロイ構成、スケーリング方針）
- 移行計画（既存データのマイグレーション等）

**成果物:**
- 技術設計書
- アーキテクチャ決定記録（ADR）
- インフラ構成図
- マイグレーション計画書（必要な場合）
- プロトタイプ/PoC（必要な場合）

**完了基準:**
- すべての技術的決定がADRに記録されている
- 実装担当者が設計を理解している（レビュー済み）
- パフォーマンス目標が定量的に定義されている

---

## 2. 設計ドキュメント要件

### 2.1 アーキテクチャ決定記録 (ADR)

アーキテクチャに関わる重要な技術的決定は、必ずADR（Architecture Decision Record）として記録する。

**ADRを作成すべき決定の例:**
- 新しいフレームワーク・言語・データベースの採用
- アーキテクチャパターンの変更（モノリス→マイクロサービス等）
- 外部サービスの採用・変更
- データストア選定
- 認証・認可方式の変更
- APIの破壊的変更

**ADRテンプレート:**

```markdown
# ADR-[番号]: [タイトル]

## ステータス
[提案中 / 承認済み / 非推奨 / 廃止]

## コンテキスト
この決定が必要になった背景と問題の説明。

## 決定事項
何を決定したか。

## 検討した代替案
| 案 | メリット | デメリット |
|---|---|---|
| 案A | ... | ... |
| 案B | ... | ... |

## 採用理由
上記の中から採用案を選んだ理由。

## 影響
この決定がシステムや開発プロセスに与える影響。

## 関連ADR
関連する他のADRへのリンク。

## 決定日
YYYY-MM-DD

## 決定者
[名前]
```

**ADRの保存場所:** `docs/adr/ADR-NNNN-title.md`

---

### 2.2 その他の設計ドキュメント

| ドキュメント種別 | 保存場所 | 更新タイミング |
|---|---|---|
| API仕様書 | `docs/api/` または Notion | APIの変更時 |
| データモデル図 | `docs/design/` | スキーマ変更時 |
| インフラ構成図 | `docs/infrastructure/` | インフラ変更時 |
| シーケンス図 | `docs/design/sequences/` | フロー変更時 |

## 3. 設計レビューチェックリスト

### 3.1 概念設計レビュー

- [ ] ビジネス要件がすべてカバーされているか
- [ ] 非機能要件（性能、セキュリティ、可用性）が考慮されているか
- [ ] 既存システムとの整合性が取れているか
- [ ] 技術的リスクが識別・評価されているか
- [ ] チームのスキルセットで実現可能か
- [ ] スケジュール・コストの見積もりが妥当か
- [ ] 複数の代替案が検討されているか

### 3.2 詳細設計レビュー

- [ ] データモデルが正規化されているか（または意図的な非正規化の理由があるか）
- [ ] APIが一貫した設計原則に従っているか（RESTful、命名規則等）
- [ ] エラーハンドリングが網羅的か
- [ ] セキュリティ要件（認証、認可、入力バリデーション）が設計されているか
- [ ] テスト戦略が明確か
- [ ] 後方互換性への影響が評価されているか
- [ ] パフォーマンスへの影響が評価されているか

### 3.3 技術設計レビュー

- [ ] 採用技術・ライブラリの選定理由が明確か（ADRがあるか）
- [ ] コードの保守性・テスト容易性が考慮されているか
- [ ] デプロイ・運用手順が考慮されているか
- [ ] 監視・ログ設計が含まれているか
- [ ] マイグレーション計画（必要な場合）が安全か
- [ ] コードレビュー観点が事前に共有されているか
- [ ] ドキュメントが最新状態に保たれているか

## 4. 設計承認ワークフロー

### 4.1 承認レベル

| 変更規模 | 承認者 | 所要時間の目安 |
|---|---|---|
| 小規模（1コンポーネント内） | Lead Engineer | 1営業日以内 |
| 中規模（複数コンポーネントまたは新機能） | Lead Engineer + 関連担当者 | 2〜3営業日以内 |
| 大規模（アーキテクチャ変更・新技術採用） | テックリード + マネージャー | 1週間以内 |

### 4.2 承認フロー

```
設計者が設計書を作成
      ↓
設計書をプルリクエスト or Notion/Confluenceに公開
      ↓
レビュワーへ通知（Linearでのメンション or Slackで連絡）
      ↓
レビュー実施（フィードバックあれば設計者が修正）
      ↓
承認者が承認（LGTM or 承認コメント）
      ↓
設計確定・実装開始
```

### 4.3 承認記録

承認は以下のいずれかの方法で記録する:
- GitHubプルリクエストのApprove機能
- Notionドキュメントへのコメントと署名
- Linear Issueへの承認コメント

## 5. 設計変更管理

### 5.1 変更の分類

| 分類 | 説明 | 対応 |
|---|---|---|
| 軽微な変更 | バグ修正・細部の調整で設計への影響が軽微 | レビューのみ（ADR不要） |
| 重要な変更 | 機能追加・インターフェース変更等 | レビュー + 設計書更新 |
| 破壊的変更 | 既存のAPIやデータ構造の破壊的変更 | ADR作成 + フル設計レビュー + 移行計画 |

### 5.2 設計変更の手順

1. **変更の影響範囲の特定:** 変更によって影響を受けるコンポーネント・API・データを洗い出す
2. **変更内容の文書化:** 変更前後の差分を設計書またはADRに記載する
3. **レビューの実施:** 変更規模に応じたレビューを行う
4. **承認の取得:** 適切な承認者から承認を得る
5. **関係者への周知:** 影響を受ける担当者・チームへの通知
6. **実装と設計書の同期:** 実装完了後に設計書が最新状態であることを確認する

### 5.3 設計ドリフトの防止

- スプリントレビュー時に設計書と実装の乖離を確認する
- ADRのステータスを定期的に見直し、非推奨・廃止になったものは更新する
- コードレビュー時に設計書との整合性を確認する項目をチェックリストに含める
