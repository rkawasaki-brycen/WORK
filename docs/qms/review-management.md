# レビュー管理プロセス

## 1. 概要

### 目的

本ドキュメントは、WORK チームにおけるコードレビュー・設計レビュー・セキュリティレビューの実施基準、チェックリスト、SLA、記録方法、および意見相違時のエスカレーションプロセスを定義する。

レビューは「欠陥の検出」だけでなく、「知識共有」「チームの品質水準の統一」「設計品質の向上」を目的とした重要な品質活動である。

### レビューの種類

| レビュー種別 | タイミング | 必須参加者 | 記録場所 |
|------------|----------|-----------|---------|
| **コードレビュー** | PR 作成後（マージ前） | Tech Lead、Developer 1 名以上 | GitHub PR コメント |
| **設計レビュー** | 実装開始前（設計フェーズ） | Tech Lead（必須）、関連 Developer | GitHub PR（設計ドキュメント更新 PR）または Notion |
| **セキュリティレビュー** | 設計フェーズおよびコードレビュー時 | Security（主担当）、Tech Lead | GitHub PR コメント / Linear Issue |

## 2. コードレビュー

### 2.1 レビュープロセスフロー

```
Developer が PR を作成（CI パス後）
    │
    ▼
`needs-review` ラベルを付与し、レビュアーをアサイン
（CODEOWNERS による自動アサインも活用）
    │
    ▼
レビュアーが初回レビューを実施（SLA: 24 時間以内）
    │
    ├─ [must] コメントあり → Developer が修正 → 再レビュー依頼
    │
    └─ [must] コメントなし → Approve
                │
                ▼
        Tech Lead + Developer 1 名以上の承認取得
                │
                ▼
        Squash merge → Linear ステート自動更新（Testing へ）
```

### 2.2 レビュアーのアサイン基準

| 変更の種類 | 最低レビュアー数 | 必須レビュアー |
|-----------|--------------|-------------|
| 通常の機能追加・バグ修正 | 2 名（Tech Lead + Developer 1 名） | Tech Lead |
| 認証・認可・セッション管理の変更 | 3 名（Tech Lead + Developer 1 名 + Security） | Tech Lead、Security |
| インフラ・CI/CD・デプロイスクリプトの変更 | 2 名（Tech Lead + DevOps 担当） | Tech Lead |
| ドキュメントのみの変更 | 1 名（担当 Developer） | なし（ピアレビューのみ） |

### 2.3 コードレビュー チェックリスト

レビュアーは以下の観点を確認する。優先度の高い順に並べており、すべてを網羅的にチェックする。

#### 【正確性・要件適合】

- [ ] 変更が Linear Issue（WORK-XXX）の受け入れ基準を満たしているか
- [ ] エッジケース・境界値が適切に処理されているか
- [ ] エラーハンドリングが実装されており、ユーザーに適切なフィードバックがあるか
- [ ] 非同期処理の競合状態（race condition）が発生しないか
- [ ] データの整合性（トランザクション、冪等性）が保たれているか

#### 【セキュリティ】

- [ ] SQL インジェクション・NoSQL インジェクションの可能性がないか
- [ ] XSS（クロスサイトスクリプティング）の可能性がないか（特に DOM 操作・HTML 出力）
- [ ] CSRF 対策が実装されているか（状態変更リクエスト）
- [ ] 認証・認可チェックが適切に実装されているか（権限昇格の可能性がないか）
- [ ] 機密情報（API キー、パスワード、個人情報）がログ出力・ハードコーディングされていないか
- [ ] 入力値バリデーションが実装されているか（サーバーサイド）
- [ ] 外部ライブラリの追加がある場合、ライセンス・脆弱性を確認したか

#### 【コード品質・保守性】

- [ ] 関数・変数名が意図を明確に表しているか
- [ ] 関数・メソッドが単一責任原則に従い、適切なサイズに収まっているか
- [ ] 重複コードが排除されており、既存の共通処理を再利用しているか
- [ ] マジックナンバー・マジック文字列が定数として定義されているか
- [ ] 型定義（TypeScript）が適切であり、`any` の使用が最小限か
- [ ] コメントが複雑なロジックに付いており、コードの「なぜ」を説明しているか

#### 【テスト】

- [ ] ユニットテストが追加・更新されており、正常系・異常系をカバーしているか
- [ ] テストが実装の詳細でなく振る舞いをテストしているか
- [ ] モック・スタブの使用が適切で、テストが本質的な部分を検証しているか
- [ ] CI のテストカバレッジが規定値（80%）を下回っていないか

#### 【パフォーマンス】

- [ ] N+1 クエリ問題が発生していないか
- [ ] 不要な再計算・再レンダリングが発生していないか
- [ ] 大量データを扱う場合にページネーション・制限が実装されているか
- [ ] 適切なキャッシュ戦略が考慮されているか

#### 【ドキュメント・その他】

- [ ] API 変更がある場合、API ドキュメント（OpenAPI 等）が更新されているか
- [ ] README や設定ファイルの変更が必要な場合、更新されているか
- [ ] 破壊的変更がある場合、PR タイトルに `!` が付与され、移行手順が記載されているか

### 2.4 レビューコメントのプレフィックス規約

| プレフィックス | 意味 | 対応の必要性 |
|-------------|-----|------------|
| `[must]` | バグ・セキュリティリスク・要件不適合。マージ前に必ず修正 | 必須（承認ブロック） |
| `[should]` | 強く推奨するが、十分な理由があれば次回対応も可 | 原則対応（理由をコメントで説明） |
| `[nit]` | 命名・スタイル等の軽微な提案。対応は任意 | 任意 |
| `[question]` | 意図や設計判断の確認。回答があれば対応不要の場合も | 回答必須 |
| `[praise]` | 良い実装への称賛。返答不要 | 不要 |
| `[idea]` | 今回のスコープ外だが将来の改善アイデア | 不要（Linear にバックログ起票を推奨） |

**コメント例**

```
[must] このクエリでユーザー入力を直接連結しています。
SQLインジェクションの危険があります。プレースホルダーを使用してください。

[should] この処理は getUserProfile() と重複しています。
共通化するとテストが容易になります。

[nit] 変数名 `d` より `dueDate` の方が読みやすいです。

[question] ここで try-catch を使用していますが、エラーを握りつぶす意図はありますか？
ログ出力か上位へのスローが必要に思われます。

[praise] 非同期エラーのハンドリングが丁寧に実装されていて参考になります。
```

### 2.5 PR 作成者の責務

レビューを依頼する前に以下を完了していること。

- [ ] ローカルでユニットテストが全てパスしている
- [ ] Lint・型チェックがパスしている（CI でも確認）
- [ ] PR 説明テンプレートの全セクションが記入されている
- [ ] セルフレビュー（自分でコードを読み返す）を実施した
- [ ] PR のサイズが 400 行以内（超える場合は分割検討または理由を記載）
- [ ] スクリーンショット・デモ動画を添付した（UI 変更の場合）

## 3. 設計レビュー

### 3.1 設計レビューが必要なケース

以下のいずれかに該当する変更は、実装開始前に設計レビューを実施する。

- 新しい API エンドポイントの追加・既存エンドポイントのインターフェース変更
- データベーススキーマの変更（テーブル追加・カラム変更・インデックス変更）
- 認証・認可・セッション管理の変更
- 外部サービス連携の新規追加（API 統合、Webhook 等）
- マイクロサービス間の通信設計変更
- 大幅なアーキテクチャ変更（モジュール分割、新技術の導入等）
- 複数スプリントにまたがる大規模機能開発の開始時

### 3.2 設計レビューの実施方法

**非同期レビュー（推奨: 小〜中規模の変更）**

1. Notion に設計ドキュメントを作成する（またはブランチに設計書ファイルを追加して PR を作成する）
2. Linear Issue に設計ドキュメントのリンクを貼り、Tech Lead にレビューを依頼する
3. Tech Lead がコメントを残し、Developer が修正・回答を行う
4. 合意に至ったら Tech Lead が「設計レビュー承認」とコメントし、実装開始を許可する

**同期レビュー（推奨: 大規模変更・複雑な設計判断）**

1. 設計ドキュメントを事前共有（レビュー会議の 1 日前まで）
2. 30〜60 分のレビュー会議を開催（Tech Lead + 関連 Developer + 必要に応じて Security）
3. 会議中の決定事項・未解決事項を Notion に記録する
4. 未解決事項は Linear Issue にコメントで記録し、フォローアップ担当者を指名する

### 3.3 設計レビュー チェックリスト

#### 【アーキテクチャ・設計】

- [ ] 既存アーキテクチャの設計原則に従っているか
- [ ] 変更が既存コンポーネントに不必要な依存関係を追加していないか
- [ ] 将来の拡張性を考慮した設計になっているか
- [ ] 過剰設計（YAGNI 原則）になっていないか

#### 【API 設計】

- [ ] RESTful / GraphQL の規約に従っているか
- [ ] エラーレスポンス形式が統一されているか
- [ ] バージョニング戦略が考慮されているか
- [ ] 後方互換性が維持されているか（破壊的変更は明示）
- [ ] レート制限・認証が適切に設計されているか

#### 【データ設計】

- [ ] スキーマの正規化レベルが適切か
- [ ] インデックス設計がクエリパターンに合致しているか
- [ ] マイグレーション計画が安全か（ダウンタイムなし、ロールバック可能）
- [ ] データの整合性制約（外部キー、ユニーク制約等）が適切か
- [ ] 個人情報・機密データの暗号化・マスキングが考慮されているか

#### 【非機能要件】

- [ ] 想定するトラフィック・データ量に対してスケールするか
- [ ] ボトルネックが特定されており、対策が検討されているか
- [ ] 障害発生時のフォールバック・回復戦略があるか

## 4. セキュリティレビュー

### 4.1 セキュリティレビューが必要なケース

すべての PR でセキュリティの観点からのチェックは行うが、以下の変更は Security エンジニアによる専門レビューが必須である。

- 認証・認可・セッション管理に関わる変更（リスクレベル: 中以上）
- 個人情報・決済情報・機密データを扱う新規機能または変更
- 外部からの入力を処理する新しいエンドポイント
- 暗号化・ハッシュ化の実装
- インフラ・ネットワーク設定の変更
- サードパーティライブラリの新規追加（重要なもの）
- セキュリティスキャン（Snyk / CodeQL）で High/Critical の脆弱性が検出された場合

### 4.2 セキュリティレビュー チェックリスト

#### 【認証・認可】

- [ ] 全エンドポイントで認証チェックが実装されているか
- [ ] ロールベースアクセス制御（RBAC）が正しく実装されているか
- [ ] JWT / セッショントークンの有効期限が適切か
- [ ] セッション固定化攻撃への対策があるか
- [ ] 権限の垂直・水平昇格が発生しないか（他ユーザーのデータへのアクセス）

#### 【入力バリデーションと出力エスケープ】

- [ ] 全ユーザー入力がサーバーサイドでバリデーションされているか
- [ ] HTML 出力が適切にエスケープされているか（XSS 対策）
- [ ] SQL / NoSQL クエリにプレースホルダー・ORM を使用しているか
- [ ] ファイルアップロードがある場合、ファイルタイプ・サイズの制限があるか
- [ ] リダイレクト先の URL が検証されているか（オープンリダイレクト対策）

#### 【機密情報の管理】

- [ ] 機密情報（APIキー、パスワード、シークレット）がコードにハードコードされていないか
- [ ] 環境変数・シークレット管理サービスを使用しているか
- [ ] ログに機密情報が出力されていないか
- [ ] エラーメッセージにシステム内部情報が含まれていないか

#### 【通信セキュリティ】

- [ ] 機密データの通信が HTTPS を使用しているか
- [ ] Cookie に `Secure`、`HttpOnly`、`SameSite` 属性が設定されているか
- [ ] CSRF トークンが実装されているか（状態変更リクエスト）
- [ ] CORS 設定が過剰に許可的でないか

#### 【依存関係】

- [ ] 新規追加ライブラリに既知の CVE がないか（Snyk で確認）
- [ ] ライセンスが商用利用可能か

### 4.3 自動セキュリティスキャンの運用

以下のツールを CI に組み込み、PR 作成時に自動実行する。

| ツール | 対象 | 検出カテゴリ | アクション |
|--------|------|-----------|-----------|
| **CodeQL** | ソースコード | SQL インジェクション、XSS 等のコード脆弱性 | High/Critical は CI をブロック |
| **Snyk** | 依存関係 | 既知の CVE | High/Critical は PR コメントでアラート |
| **GitLeaks** | コミット | シークレットの漏洩 | 検出時は即座に CI をブロック |

**スキャン結果の対応方針**

| 深刻度 | 対応方針 | 期限 |
|--------|---------|------|
| Critical | PR ブロック。Security による確認後にのみマージ許可 | 即時 |
| High | PR コメントに警告。Security の確認を要求 | 48 時間以内 |
| Medium | PR コメントに通知。次スプリントでの対応を検討 | 次スプリント内 |
| Low | GitHub Security タブに記録。バックログ管理 | 計画的に対応 |

## 5. レビュー SLA

### 5.1 初回レビュー SLA

レビュー依頼（`needs-review` ラベル付与 or アサイン）を受けてから初回コメントを返すまでの目標時間。

| 優先度 | SLA | 適用条件 |
|--------|-----|---------|
| 通常 | 24 時間以内（営業日） | 通常の `needs-review` ラベル |
| 緊急 | 4 時間以内 | `urgent` ラベル付き PR |
| ホットフィックス | 30 分以内 | `hotfix` ブランチの緊急 PR |

### 5.2 レビューサイクル SLA

レビューコメントへの返答・修正については以下を目安とする。

| アクション | SLA |
|-----------|-----|
| `[must]` コメントへの修正 | 翌営業日以内 |
| `[should]` コメントへの対応判断の回答 | 翌営業日以内 |
| `[question]` への回答 | 当日中（営業時間内） |
| 修正後の再レビュー | 再依頼後 24 時間以内 |

### 5.3 SLA 違反時の対応

- **24 時間経過してもレビューが開始されない場合**: PR 作成者が Slack でリマインドを送る
- **48 時間経過してもレビューが完了しない場合**: PM または Tech Lead にエスカレーション
- **スプリント期限に間に合わない場合**: Tech Lead が代替レビュアーを指名する

## 6. GitHub でのレビューアウトカムの記録

### 6.1 承認（Approve）

以下の条件を全て満たした場合にのみ Approve する。

- コードレビューチェックリストの全項目を確認した
- `[must]` コメントが全件解消されている
- CI が green であることを確認した
- 対象の変更に応じたセキュリティ確認が完了している

Approve 時は以下のコメントを残すことを推奨する。

```
LGTM。コードレビューチェックリスト確認済み。
```

（必要に応じて良かった点や補足事項を追記する）

### 6.2 修正要求（Request Changes）

`[must]` または重大な `[should]` コメントがある場合は **Request changes** を選択する。

```
[must] コメントが X 件あります。修正後に再レビューをお願いします。

主な指摘事項:
1. [must] XX のセキュリティリスク
2. [must] YY の処理漏れ
```

### 6.3 レビュー結果の Linear への反映

- コードレビュー通過 → Linear の自動連携で `Testing` ステートへ移行（PR マージ後）
- セキュリティレビューで重大な問題を発見した場合 → Linear Issue に `risk:high` ラベルを付与し、Security がコメントを追記する
- 設計レビューの結果 → Linear Issue コメントに承認記録または差し戻し理由を記載する

## 7. レビュー意見相違時のエスカレーション

### 7.1 意見相違のレベル分類

レビューコメントに対して PR 作成者とレビュアーの意見が合わない場合、以下のレベルに分類して対処する。

| レベル | 定義 | 対処方法 |
|--------|------|---------|
| **Level 1** | 命名・スタイルの好みの違い | PR 作成者の判断を尊重する |
| **Level 2** | 技術的実装アプローチの違い（どちらも正しい） | 技術的なトレードオフを議論し合意する。合意できない場合は Level 3 へ |
| **Level 3** | 設計・アーキテクチャ上の根本的な不一致 | Tech Lead が最終判断を下す |
| **Level 4** | セキュリティリスクの認識の違い | Security が最終判断を下す。CTO への報告も検討 |

### 7.2 エスカレーションプロセス

```
【Step 1】PR コメントで議論する（24 時間以内に解決を目指す）
    │
    ▼ 解決しない場合
【Step 2】Slack の開発チャンネルで同期的に議論する（30 分以内）
    │
    ▼ 解決しない場合
【Step 3】Tech Lead が判断を下す
    │   （セキュリティ案件は Security が判断）
    │
    ▼ Tech Lead も判断しきれない場合（アーキテクチャ上の重大な問題）
【Step 4】CTO に最終判断を仰ぐ
```

### 7.3 エスカレーション時の原則

- **PR をブロックし続けることを避ける**: SLA を超過する前に Level を上げる
- **人ではなくコードを批判する**: 意見の相違は個人攻撃でなく技術的議論として扱う
- **最終判断は記録に残す**: Tech Lead または CTO の判断はコメントとして PR に記録する
- **判断の根拠を残す**: 将来の参照のため、なぜその判断をしたかを記録する

**エスカレーションコメント例**

```
Tech Lead の判断を仰ぎたいと思います @tech-lead-name

【背景】
○○の実装について、以下 2 つのアプローチで意見が分かれています。

【アプローチ A（レビュアー案）】
○○の方法。メリット: ○○、デメリット: ○○

【アプローチ B（実装者案）】
○○の方法。メリット: ○○、デメリット: ○○

判断をお願いします。
```

## 8. レビュープロセスの改善

### 8.1 レビュー品質メトリクス

以下のメトリクスを月次でトラッキングし、レビュープロセスの改善に活用する。

| メトリクス | 計測方法 | 目標 |
|-----------|---------|------|
| 平均初回レビュー時間 | GitHub PR データ | 24 時間以内 |
| `[must]` コメント 1 PR あたりの平均件数 | PR コメント集計 | 月次でトレンドを確認 |
| レビューサイクル数（PR あたり） | PR の review コメントラウンド数 | 平均 2 以内 |
| 本番流出バグのうちレビューで防げた率 | インシデント事後分析 | トレンド改善 |

### 8.2 定期的なチェックリスト見直し

- 本番インシデントが発生した場合、ポストモーテムでチェックリストへの追加を検討する
- スプリントレトロスペクティブで「レビューで見逃したパターン」を共有し、必要に応じてチェックリストを更新する
- チェックリストの更新は本ドキュメントへの PR を通じて行い、Tech Lead が承認する
