# 継続的改善プロセス

## 目的

本文書は、チームおよびプロセスの継続的な改善を推進するための手順を定める。定期的な振り返りとメトリクスの追跡を通じて、問題を早期に発見し、具体的な改善アクションにつなげることで、チームのパフォーマンスと製品品質を継続的に向上させる。

## 適用範囲

本プロセスは開発チームのすべてのメンバーに適用する。また、定期的なマネジメントレビューを通じて経営層との連携も行う。

---

## 1. レトロスペクティブ（振り返り）プロセス

### 1.1 スプリントレトロスペクティブ

**実施タイミング:** 各スプリント終了時（2週間に1回を基本とする）

**所要時間:** 60〜90分

**参加者:** 開発チームメンバー全員、スクラムマスター/ファシリテーター

**目的:**
- スプリント中の良い点・問題点を振り返る
- 具体的な改善アクションを特定する
- 前回のアクションアイテムの進捗を確認する

**ファシリテーション原則:**
- 心理的安全性を確保する（批判より学習を重視）
- 人ではなくプロセスを改善対象とする
- 全員が発言できる環境を作る
- アクションは具体的・測定可能・担当者が明確なものにする

---

### 1.2 四半期レトロスペクティブ

**実施タイミング:** 四半期終了時（年4回）

**所要時間:** 2〜3時間

**参加者:** 開発チームメンバー全員、エンジニアリングマネージャー、プロダクトマネージャー

**目的:**
- 四半期を通じた傾向と大きな問題を把握する
- スプリントレトロでは扱いきれない組織・プロセスの課題を議論する
- 次の四半期の改善目標を設定する
- メトリクスのトレンドを分析する

---

## 3. 追跡するメトリクス

### 3.1 開発速度・効率メトリクス

#### ベロシティ (Velocity)
- **定義:** 1スプリントで完了したストーリーポイント数
- **追跡方法:** Linear またはスプレッドシートで記録
- **目標:** 安定した予測可能なペースを維持する（急激な変動を避ける）
- **確認頻度:** スプリントごと

#### リードタイム (Lead Time)
- **定義:** Issueが作成されてからリリースされるまでの時間
- **内訳:**
  - 待機時間（作成〜開発開始）
  - 開発時間（開発開始〜PRマージ）
  - デプロイ時間（マージ〜本番リリース）
- **確認頻度:** 週次でトレンドを確認

#### サイクルタイム (Cycle Time)
- **定義:** 開発を開始してから完了するまでの時間
- **目標:** 機能開発は3日以内、バグ修正は1日以内（目安）
- **確認頻度:** スプリントごと

---

### 3.2 品質メトリクス

#### バグ発生率 (Defect Rate)
- **定義:** リリースしたStory Pointあたりの本番バグ数
- **算出方法:** 月次バグ数 ÷ 月次リリースStory Points
- **目標値:** 前月比を下回る、または業界標準以下
- **確認頻度:** 月次

#### バグ検出タイミング
- **定義:** バグが発見された環境の割合（開発/テスト/ステージング/本番）
- **目標:** 本番環境での発見を減らし、早期発見を増やす
- **確認頻度:** 月次

#### コードカバレッジ
- **定義:** 自動テストによってカバーされているコードの割合
- **目標:** 70%以上を維持（増加傾向を目指す）
- **確認頻度:** 週次（CI/CDパイプラインで自動計測）

---

### 3.3 デリバリーメトリクス (DORAメトリクス)

#### デプロイ頻度 (Deployment Frequency)
- **定義:** 本番環境へのデプロイ回数（週または日あたり）
- **目標:** 週2回以上（高パフォーマンス目標: 毎日）
- **確認頻度:** 月次

#### 変更リードタイム (Change Lead Time)
- **定義:** コードのコミットから本番稼働までの時間
- **目標:** 1日以内（高パフォーマンス目標: 1時間以内）
- **確認頻度:** 月次

#### 変更失敗率 (Change Failure Rate)
- **定義:** デプロイのうち、本番障害を引き起こした割合
- **算出方法:** 障害・ロールバック件数 ÷ 総デプロイ件数 × 100
- **目標:** 15%以下（高パフォーマンス目標: 5%以下）
- **確認頻度:** 月次

#### 平均復旧時間 (MTTR: Mean Time To Recovery)
- **定義:** 本番障害発生から復旧するまでの平均時間
- **目標:** 1時間以内（高パフォーマンス目標: 30分以内）
- **確認頻度:** 月次（障害発生時のみ）

---

### 3.4 メトリクスダッシュボード

メトリクスは以下の方法で可視化・管理する:
- **リアルタイムメトリクス:** 監視ツール（Datadog、CloudWatch等）のダッシュボード
- **開発メトリクス:** Linearのレポート機能またはスプレッドシート
- **月次サマリ:** Notionの「メトリクスログ」ページに記録

## 4. 改善バックログ管理

### 4.1 改善アイテムの記録

レトロスペクティブで特定された改善アクションは、改善バックログとして管理する。

**記録方法:**
- Linearに専用ラベル「improvement」を付けてIssueを作成する
- または「Improvement Backlog」スプレッドシートに記録する

**記録すべき情報:**
```
タイトル: 改善アクションの概要
カテゴリ: [プロセス / ツール / スキル / コミュニケーション / 技術]
詳細: 何を改善するか、どのような効果を期待するか
優先度: [高 / 中 / 低]
工数見積: [〜1時間 / 半日 / 1日 / 1週間以上]
担当者: @username（未定の場合は空欄）
期限: YYYY-MM-DD（未定の場合は「要決定」）
関連メトリクス: この改善で改善が期待されるメトリクス
出典: [Sprint XX レトロ / 四半期レトロ / インシデント対応]
```

### 4.2 改善バックログのリファインメント

**頻度:** 月1回（または四半期レトロスペクティブ前）

**内容:**
- バックログアイテムの優先度を見直す
- 完了済みアイテムをクローズする
- 古くなった（不要になった）アイテムを棚卸しする
- 次の1ヶ月で対応するアイテムを決定する

### 4.3 改善アクションの優先順位付け

以下の観点で優先度を評価する:

| 評価軸 | 高優先度 | 低優先度 |
|---|---|---|
| 影響度 | チーム全体・重要メトリクスへの影響 | 個人・軽微な影響 |
| 緊急度 | 繰り返し発生している問題 | 一度だけの問題 |
| 実現可能性 | 少ない工数で実施可能 | 大きな工数が必要 |
| 依存関係 | 他の改善の前提となる | 独立した改善 |

## 5. 組織的な問題のエスカレーション

### 5.1 エスカレーションが必要な問題

以下の状況では、チーム内での解決を超えてエスカレーションを行う:

- 同じ問題が3回以上のレトロスペクティブで繰り返し挙がっている
- 問題の解決に他チームや経営層の関与が必要
- 予算・採用・組織構造に関わる問題
- コンプライアンス・法的リスクに関わる問題
- チーム内のコンフリクトがプロセス改善で解決できない

### 5.2 エスカレーションの手順

```
1. 問題の文書化
   - 問題の詳細と発生頻度
   - チーム内で試みた解決策と結果
   - この問題が解決されない場合のリスク
   - 解決に必要なリソース・権限

2. エスカレーション先の特定
   - エンジニアリングマネージャー（技術・プロセスの問題）
   - プロダクトマネージャー（プロダクト優先度の問題）
   - 経営層（組織・予算の問題）

3. 1on1またはミーティングで報告
   - 問題の背景と現状を説明する
   - 具体的な支援・判断を依頼する

4. フォローアップ
   - エスカレーション後2週間以内に進捗を確認する
   - 解決策が実行されているかをトラッキングする
```

### 5.3 エスカレーション記録

エスカレーションした問題は改善バックログに「エスカレーション中」ステータスで記録し、対応状況を追跡する。

## 6. 年次マネジメントレビュー

### 6.1 目的

年に1回、経営層を含む関係者全員で、品質マネジメントシステム全体の有効性を評価し、次年度の改善方針を決定する。

### 6.2 実施タイミング

- 年度末（または第4四半期終了後）に実施する
- 所要時間: 3〜4時間（半日）
- 事前準備: 2週間前から資料を作成・共有する

### 6.3 参加者

- エンジニアリングマネージャー（必須）
- テックリード（必須）
- プロダクトマネージャー（必須）
- 経営層（CTO、CEOなど）（推奨）
- 開発チームの代表者（任意）

### 6.4 アジェンダ

| 時間 | トピック | 内容 |
|---|---|---|
| 30分 | 年間メトリクスレビュー | 1年間のDORAメトリクス、品質メトリクスのトレンド確認 |
| 45分 | QMSプロセスの有効性評価 | 各QMSプロセス（設計/変更/リリース/継続改善）の振り返り |
| 30分 | 重大インシデントの振り返り | 年間で発生した重大インシデントの傾向分析 |
| 45分 | 次年度改善目標の設定 | 改善バックログの整理、次年度の重点改善領域の決定 |
| 30分 | リソース・予算の議論 | 改善に必要なリソースの確認・調整 |

### 6.5 アウトプット

マネジメントレビューの結果として以下を作成する:
- **年次レビューレポート:** 年間メトリクス、主要な成果、課題のサマリ
- **次年度改善計画:** 重点改善領域、目標値、担当者、タイムライン
- **QMSプロセス改訂計画:** 更新が必要なQMS文書と改訂スケジュール

これらはNotionに保存し、チーム全員がアクセス可能な状態にする。

## 7. 継続的改善の文化づくり

### 7.1 心理的安全性の維持

継続的改善が機能するためには、失敗を責めない文化が不可欠である:
- 問題が発生した場合は「誰が悪いか」ではなく「何が原因か」を追求する
- 改善提案をした人を評価する
- 「このプロセスはうまく機能していない」と言える環境を維持する

### 7.2 小さな改善の積み重ね

大きな変革よりも、小さな改善を積み重ねることを重視する:
- 1スプリントに1〜2個の改善アクションを実施することを目標にする
- 完璧な解決策を待たずに、試行を早期に始める
- 改善の効果を測定し、フィードバックループを回す

### 7.3 改善の共有

改善の成果はチーム内外に共有する:
- 効果的だった改善はSlackで共有する
- 大きな改善は他チームとも共有する（社内Tech Blog等）
- 失敗した改善からの学びも記録・共有する
