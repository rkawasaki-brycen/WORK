## コンテキスト

プロジェクトの成長に伴い、過去のアーキテクチャ上の意思決定とその背景が失われるという問題が顕在化してきた。具体的には以下のような課題があった。

- **意思決定の文脈の喪失**: なぜ現在の技術スタックや設計を採用したのかが分からず、変更の判断が困難になる
- **知識のサイロ化**: 特定のメンバーだけが過去の経緯を把握している状態が生まれる
- **議論の重複**: 過去に検討・却下した選択肢を再度議論するための無駄なコストが発生する
- **オンボーディングの非効率**: 新しいメンバーがアーキテクチャの全体像と経緯を把握するのに多大なコストがかかる

これらの課題を解決するために、アーキテクチャ上の重要な意思決定を体系的に記録・管理する仕組みの導入を検討した。

## 決定内容

我々は、アーキテクチャ決定記録（Architecture Decision Records、ADR）を採用し、重要なアーキテクチャ上の意思決定をコードリポジトリ内の `docs/adr/` ディレクトリに Markdown ファイルとして記録・管理することにした。

ADRのフォーマットは Michael Nygard が提唱したオリジナル形式をベースに、チームのニーズに合わせて拡張したカスタム形式を使用する。具体的には、選択肢の比較表・リスク欄・関連情報欄を追加したテンプレートを `docs/adr/adr-template.md` として定義し、全ADRはこのテンプレートに従って記述する。

## 根拠

### ADRを採用する理由

ADRはソフトウェア業界で広く実績のある軽量な手法であり、以下の点でチームの課題に適合していると判断した。

- テキストファイルとしてコードと同一リポジトリで管理できるため、コードの変更と意思決定記録を同一PRで追跡できる
- 記述フォーマットがシンプルで学習コストが低く、継続的な運用が現実的である
- バージョン管理システムによって変更履歴が自動的に保存される
- ステータス管理（Proposed / Accepted / Deprecated / Superseded）により、決定の有効性を明示できる

### カスタムフォーマットを選んだ理由

既存の標準フォーマットを検討した結果、完全な準拠よりもカスタムフォーマットの採用が適切と判断した。詳細は選択肢の比較を参照。

## 選択肢の比較

| 選択肢 | メリット | デメリット |
|--------|----------|------------|
| **カスタムフォーマット（採用）** | チームのニーズに合わせた構成が可能。選択肢比較表・リスク欄を標準化できる。日本語で記述できる | 業界標準ツールとの互換性がない場合がある |
| **Nygard オリジナル形式** | 最もシンプルで広く知られている。参考文献が豊富 | 選択肢比較・リスク管理の欄がなく、情報が不足しやすい |
| **MADR（Markdown Architectural Decision Records）** | 構造化された比較テーブルを持ち、ツールサポートがある。GitHub上でのレンダリングが良好 | 英語前提の設計であり、日本語チームへの適用に若干の摩擦がある |
| **Y-Statements形式** | 一文で決定を表現できる簡潔さがある | 複雑な意思決定の記録には情報量が不足する |
| **Confluence等のWikiツール** | リッチな編集機能と検索性がある | コードとの乖離が生じやすく、メンテナンスが疎かになりやすい |

## 影響・結果

**ポジティブな影響**
- アーキテクチャ上の意思決定が検索・参照可能な形で蓄積される
- 新メンバーのオンボーディング時間を短縮できる
- 技術的負債の意図的な受け入れと、その返済計画を記録できる
- PRレビュー時に、なぜその実装を選んだかの参照先を提供できる

**コストと変化**
- 重要な技術的意思決定の際にADRを作成する習慣を定着させるコストがかかる
- ADRのレビューがPRレビューの一部となり、レビュー工数が若干増加する
- ドキュメントが古くなるリスクがあり、定期的な棚卸しが必要

## リスク・懸念事項

**運用が形骸化するリスク**
- リスク: 最初は書いていても、プロジェクトが忙しくなると書かれなくなる
- 対策: 「いつADRを書くか」の基準を明確にし（README参照）、PRテンプレートにADR確認項目を追加することを検討する

**粒度が不揃いになるリスク**
- リスク: 書く人によって、ADRに記録される意思決定の重要度が大きくばらつく
- 対策: README に「いつADRを書くか」のガイドラインを明示し、チームで定期的に見直す

**陳腐化するリスク**
- リスク: 時間の経過とともにADRの内容が実態と乖離する
- 対策: 意思決定が覆された場合は必ず元のADRを `Superseded` に更新し、新しいADRを作成する運用を徹底する
