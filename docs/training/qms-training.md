# QMS（品質マネジメントシステム）トレーニング

**対象:** チームメンバー全員
**所要時間:** 約45分
**更新日:** 2026-06-12

---

## 1. なぜ品質管理が必要か

### 1.1 品質管理は「認証のため」ではない

「QMS」「ISO 9001」という言葉を聞くと、認証取得のための書類作業のように感じるかもしれません。しかし私たちの QMS の目的はそこにありません。

**品質管理が本当に目指すもの:**

- **手戻りコストの削減**: バグを後工程で発見するほど修正コストが増大します。要件定義段階で発見したバグの修正コストを 1 とすると、テスト段階では 10 倍、本番リリース後では 100 倍以上になると言われています。
- **予測可能な開発**: プロセスが整備されることで、見積もり精度が向上し、スプリント計画が現実的になります。
- **チームへの信頼**: 品質の高い成果物を継続的に届けることが、顧客・ステークホルダーからの信頼につながります。
- **個人のストレス軽減**: 「本番で何か起きないか不安」という状態は、適切なプロセスによって大幅に軽減されます。

### 1.2 小さいチームこそ品質管理が重要

5〜20名の小規模チームでは、一人の問題が全体に波及します。「みんな忙しいからレビューをスキップしよう」という判断が積み重なると、技術的負債が蓄積し、最終的にはチーム全体の生産性を下げます。

## 2. 開発ライフサイクル概要

私たちの開発は以下のフェーズで構成されています。詳細は `docs/development-lifecycle.md` を参照してください。

```
要件定義 → 設計 → リスクレビュー → 実装 → PR作成 → コードレビュー → テスト → リリース → レトロスペクティブ
```

### 各フェーズのポイント

| フェーズ | 主な目的 | 品質ゲート |
|---------|---------|-----------|
| 要件定義 | 何を作るかの合意 | PM + Tech Lead の承認 |
| 設計 | どう作るかの計画 | Tech Lead によるレビュー |
| リスクレビュー | セキュリティ・リスクの評価 | Security によるリスク評価 |
| 実装 | コードの作成 | 自己レビュー、ローカルテスト全パス、CI 通過 |
| コードレビュー | 複数の目でコードを確認 | Tech Lead + Developer 1名以上の承認 |
| テスト | 要件が満たされているか確認 | 全テストパス、重篤バグゼロ |
| リリース | 本番環境への反映 | ステークホルダー全員の GO 確認 |

### ブランチとコミットのルール

```
ブランチ名: feature/<linear-issue-id>-<short-description>
例:         feature/ENG-123-add-user-profile

コミット:   [ENG-123] ユーザープロファイル機能の追加

main ブランチへの直接プッシュは禁止です。
```

## 3. あなたの役割: Definition of Done（完了の定義）

チケットを「完了」とするには、以下のすべての条件を満たす必要があります。**「だいたいできた」は完了ではありません。**

### コード品質

- [ ] 受け入れ基準を 100% 満たしている
- [ ] Lint / Format チェックが通過している
- [ ] TypeScript の型エラーがゼロ
- [ ] 自己レビューが完了している（PR セルフレビューチェックリスト全項目）

### テスト

- [ ] ユニットテストが追加・更新され、CI でパスしている
- [ ] テストカバレッジが 80% 以上を維持している
- [ ] 統合テストが通過している
- [ ] QA による受け入れテストが完了・承認されている

### レビュー・承認

- [ ] Tech Lead が承認している
- [ ] Developer 1名以上がピアレビューを完了・承認している
- [ ] セキュリティリスクが評価され、必要に応じて Security が承認している
- [ ] `[MUST]` コメントが全件対応済み

### ドキュメント

- [ ] API 変更がある場合はドキュメントが更新されている
- [ ] 環境変数変更がある場合は README が更新されている
- [ ] ユーザー影響がある変更はリリースノートに記載されている

## 4. 受け入れ基準の書き方

受け入れ基準（Acceptance Criteria）は、「この機能が完成した」と言えるための条件を具体的に定義したものです。曖昧な受け入れ基準は、後工程での認識違いや手戻りの原因になります。

### 良い受け入れ基準の特徴

- **具体的**: 「使いやすい」ではなく、「3ステップ以内で登録が完了する」
- **テスト可能**: 合否を客観的に判断できる
- **ユーザー視点**: 技術実装の詳細ではなく、ユーザーが体験することを記述する

### Given-When-Then 形式（推奨）

```
Given（前提条件）: ログイン済みのユーザーが
When（操作）: プロフィール編集画面で名前を変更して「保存」ボタンを押すと
Then（期待結果）: 変更した名前がプロフィール画面に反映され、「保存しました」のメッセージが表示される

Given（前提条件）: ログイン済みのユーザーが
When（操作）: 名前を空のまま「保存」ボタンを押すと
Then（期待結果）: 「名前を入力してください」のエラーメッセージが表示され、保存されない
```

### 受け入れ基準のチェックリスト

受け入れ基準を書いたら、以下を確認してください。

- [ ] 正常系（ハッピーパス）が書かれているか
- [ ] 異常系（エラーケース・境界値）が考慮されているか
- [ ] 誰が読んでも同じ理解になるか
- [ ] テスト可能な形式になっているか

## 5. レビューの依頼方法

### PR を作成する前に

1. **ローカルで全テストを実行する**（`npm test`）
2. **Lint チェックを実行する**（`npm run lint`）
3. **自分でコードを読み直す**（自己レビューチェックリストを使う）
4. **差分が大きすぎないか確認する**（目安: 400行以内。大きい場合は分割を検討）

### PR 作成時に含めるべき情報

```markdown
## 変更概要
何を・なぜ変更したかを 3〜5行で説明する

## 関連チケット
Fixes ENG-123

## 変更の種類
- [ ] 新機能
- [ ] バグ修正
- [ ] リファクタリング
- [ ] ドキュメント
- [ ] その他

## テスト方法
どのように動作確認したかを記述する
（例: ローカルで○○画面を操作し、□□が表示されることを確認した）

## スクリーンショット（UI変更がある場合）

## 特に注意してレビューしてほしい点
レビュアーに重点的に見てほしい箇所があれば記載する

## セルフレビューチェックリスト
- [ ] コードを自分で読み直した
- [ ] テストが追加されている
- [ ] ドキュメントが更新されている（必要な場合）
- [ ] 機密情報が含まれていない
```

### レビューコメントの読み方

| ラベル | 意味 | 対応 |
|--------|------|------|
| `[MUST]` | 修正必須（マージ前に対応が必要） | 必ず修正してから再依頼 |
| `[SHOULD]` | 修正を推奨（合意の上で次回対応も可） | 対応するか否かを明示してコメント返信 |
| `[NIT]` | 細かい提案（対応任意） | 対応しない場合は無視してもよい |
| `[QUESTION]` | 疑問・確認事項 | 回答・説明をコメントで返す |

## 6. 品質問題の報告方法

バグや品質上の問題を発見した場合は、Linear にチケットを起票してください。

### バグレポートに含める情報

```
タイトル: [バグ] ○○画面で□□すると△△が発生する

説明:
- 発生環境: ステージング / 本番
- 発生日時: YYYY-MM-DD HH:MM
- 影響範囲: 全ユーザー / 特定の条件

再現手順:
1. ○○画面を開く
2. □□を入力する
3. 「送信」ボタンを押す

期待される動作:
（どうなるべきだったか）

実際の動作:
（実際に何が起きたか）

添付:
- スクリーンショット
- エラーログ（機密情報を含まない形で）
```

### バグの優先度

| 優先度 | 定義 | 対応期限 |
|--------|------|---------|
| Critical | データ破損・セキュリティ侵害・サービス停止 | 即時（リリースブロック） |
| High | 主要機能の動作不良 | リリース前必須修正 |
| Medium | 一部機能の不具合（回避策あり） | 当スプリント内 |
| Low | 軽微な UI 問題 | バックログ登録 |

セキュリティに関わる問題は、公開チャンネルではなく `#security-incidents` または Security 担当者に直接報告してください。

## 7. 私たちが追跡している指標

指標を把握することで、チームの健全性を客観的に評価できます。

| 指標 | 目標値 | なぜ重要か |
|------|--------|-----------|
| テストカバレッジ（ユニット） | 80% 以上 | 低いカバレッジはテストされていないコードがあることを示す |
| Critical/High バグの本番流出 | 0 件/月 | 本番で重大バグが発生すると顧客信頼を損なう |
| PR レビュー SLA（24h 以内） | 90% 以上 | レビュー待ちの長期化はスプリント遅延の主要因になる |
| スプリント完了率 | 80% 以上 | 見積もりと実績の乖離が大きいと計画の信頼性が下がる |
| ホットフィックス発生頻度 | 月 1 回以下 | 頻発するホットフィックスはプロセスの問題を示す |
| 本番インシデントの MTTR | 2 時間以内 | 障害対応の速さは顧客影響の最小化に直結する |

これらの指標は毎週のスプリントレビューと毎月の報告で確認します。悪化傾向があれば、レトロスペクティブで原因を議論し、改善アクションを立案します。

### レトロスペクティブ（KPT）への参加

スプリント終了時に行うレトロスペクティブは、チームのプロセス改善の場です。積極的に参加してください。

- **Keep**: うまくいったこと・継続したいこと
- **Problem**: 問題だったこと・改善したいこと
- **Try**: 次のスプリントで試してみること

---

## 8. まとめ: 品質はチーム全員の仕事

QMS は特定の役割（QA や Tech Lead）だけの仕事ではありません。

- **Developer**: テストを書く、自己レビューをする、受け入れ基準に沿って実装する
- **Reviewer**: 建設的なフィードバックを 24 時間以内に行う
- **全員**: バグを発見したら報告する、プロセスの問題に気づいたら声を上げる

「誰かがやるだろう」という意識を捨て、品質に対してオーナーシップを持ちましょう。
