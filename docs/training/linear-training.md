## 1. Linear の基礎

### チーム（Team）

チームはプロダクト・機能領域ごとに区切られた作業単位です。各チームは独自のワークフロー、サイクル、バックログを持ちます。

```
組織（Workspace）
 ├── Team: Frontend
 ├── Team: Backend
 ├── Team: Infrastructure
 └── Team: Design
```

イシューを作成する際は、必ず正しいチームに属するよう選択してください。

### プロジェクト（Project）

プロジェクトは複数のイシューをまとめた大きな作業のまとまりです。特定のリリースや機能開発に使います。

```
例:
Project: ユーザー認証システムのリニューアル
 ├── LIN-101: ログインページの UI 刷新
 ├── LIN-102: OAuth2 対応（Google ログイン）
 ├── LIN-103: 多要素認証（MFA）の実装
 └── LIN-104: セッション管理の改善
```

### イシュー（Issue）

イシューは個々のタスクや作業アイテムです。Linear における最小の作業単位です。

**イシューの構成要素**

| フィールド | 説明 |
|---|---|
| タイトル | 作業内容を簡潔に表す（後述） |
| 説明 | 背景・要件・完了条件 |
| ステータス | 現在の進行状態 |
| 優先度 | Urgent / High / Medium / Low / No priority |
| 担当者 | 作業者 |
| ラベル | カテゴリ分類（bug, feature, docs など） |
| サイクル | 所属するスプリント |
| プロジェクト | 所属するプロジェクト |
| 見積もり | ストーリーポイント（1, 2, 3, 5, 8 など） |

### サイクル（Cycle）

サイクルはスプリントに相当します。2 週間ごとに区切られた作業期間です。

```
サイクル #42（2026-06-15 〜 2026-06-28）
 ├── 計画済み: 18 ポイント
 ├── 進行中:    6 ポイント
 └── 完了:     12 ポイント
```

## 2. ワークフローステータスの使い方

### ステータスの一覧と使用タイミング

| ステータス | 意味 | 移動するタイミング |
|---|---|---|
| `Backlog` | 未着手・優先度未定 | イシュー作成直後（デフォルト） |
| `Todo` | 着手予定・優先度確定済み | スプリント計画でサイクルに追加したとき |
| `In Progress` | 作業中 | 実際にコードを書き始めたとき |
| `In Review` | レビュー待ち | PR を作成してレビューを依頼したとき |
| `Done` | 完了 | PR がマージされ、動作確認が完了したとき |
| `Cancelled` | キャンセル | 不要になったとき（理由をコメントで残す） |

### ステータス変更のフロー例

```
作業開始時:
  Backlog → Todo（スプリント計画）
  Todo → In Progress（作業開始時に自分で変更）

作業中:
  In Progress → In Review（PR 作成後）

完了時:
  In Review → Done（PR マージ後・動作確認済み）
```

**注意事項**
- ステータスは自分で変更する（自動化はされていない）
- `In Progress` のイシューは作業中に必ず 1 つのブランチと対応させる
- 長期間 `In Progress` のまま放置しない（スタンドアップで報告する）

## 3. 良いイシューの書き方

### タイトルの書き方

タイトルは「動詞 + 対象 + 目的」の形式で書くと明確になります。

```
良い例:
  ユーザーログイン時のエラーメッセージを日本語化する
  商品一覧ページにカテゴリフィルターを追加する
  パスワードリセットメールの送信失敗バグを修正する

悪い例:
  ログイン修正
  フィルター
  バグ対応
```

### 説明の書き方

説明には以下の要素を含めます。

**機能追加・改善の場合**

```markdown
## 背景・目的
ユーザーから「エラーメッセージが英語で分からない」というフィードバックが
複数寄せられています。日本語化することでユーザー体験を改善します。

## 要件
- ログイン失敗時のエラーメッセージを日本語で表示する
- 対象メッセージ:
  - Invalid email or password → 「メールアドレスまたはパスワードが正しくありません」
  - Account locked → 「アカウントがロックされています。サポートにお問い合わせください」

## 完了条件（Definition of Done）
- [ ] 全エラーメッセージが日本語で表示される
- [ ] 英語ロケールでは英語のまま表示される
- [ ] テストが追加されている
- [ ] デザイナーによる確認が完了している
```

**バグ報告の場合**

```markdown
## バグの概要
ログアウト後にもセッションが残り、再度ブラウザを開くとログイン状態になる

## 再現手順
1. ログインする
2. 「ログアウト」ボタンをクリックする
3. ブラウザを閉じて再度開く
4. アプリにアクセスするとログイン状態になっている

## 期待する動作
ログアウト後はセッションが無効化され、再アクセス時はログインページが表示される

## 環境
- ブラウザ: Chrome 125, Safari 18
- 発生頻度: 毎回再現

## 影響範囲
セキュリティ上の問題のため、優先度 High で対応が必要
```

## 4. 優先度の設定ガイドライン

### 優先度の定義

| 優先度 | 定義 | 対応目安 |
|---|---|---|
| Urgent | 本番障害・セキュリティ脆弱性・SLA 違反 | 即日対応 |
| High | 主要機能のバグ・リリースブロッカー | 当スプリント内 |
| Medium | 改善要望・軽微なバグ・技術的負債 | 次スプリントまで |
| Low | 将来的な改善・あると嬉しい機能 | バックログで管理 |
| No priority | 検討中・優先度未定 | 次回のスプリント計画で判断 |

### 優先度の判断フロー

```
本番環境に影響している?
  ├── Yes → Urgent（すぐに担当者に連絡）
  └── No
      ↓
主要機能が使えない / リリース日程に影響する?
  ├── Yes → High
  └── No
      ↓
ユーザーへの影響はあるが回避策がある?
  ├── Yes → Medium
  └── No → Low
```

### 優先度変更のルール

- 自分のイシュー以外の優先度を変更する場合は、変更理由をコメントに記載する
- `Urgent` に設定する場合は、チームリードへの即時通知が必要

## 5. Linear イシューと GitHub PR の連携

### 連携の仕組み

Linear と GitHub を連携することで、以下が自動化されます。

- ブランチ名にイシュー ID を含めると Linear イシューに PR が自動紐付けされる
- PR のマージでイシューが自動的に `Done` に移動する
- PR のステータスが Linear のイシュー画面に表示される

### ブランチ名による自動連携

```bash
# イシュー ID をブランチ名に含める
git checkout -b feature/lin-123-add-user-profile
#                     ^^^^^^^^
#                     Linear のイシュー ID（小文字でも可）

# または Linear の「Create branch」ボタンから作成すると自動設定される
```

### PR の説明に Linear イシューを記載する

PR の説明に以下の形式でイシューを参照すると、マージ時に自動的に `Done` に移動します。

```markdown
Closes LIN-123

または

Fixes LIN-123
Resolves LIN-123
```

### Linear の「Create branch」機能の使い方

1. Linear でイシューを開く
2. 右上の「...」メニューから「Create branch」を選択
3. ブランチ名が自動提案される（変更可能）
4. ターミナルでコマンドをコピーして実行

```bash
# Linear が提案するコマンド例
git checkout -b feature/lin-123-add-user-profile origin/develop
```

## 6. スプリントセレモニー

### スプリント計画（Sprint Planning）

**実施タイミング**: 毎スプリント開始日（2 週間ごと月曜日）10:00〜11:30

**目的**: 次のスプリントで取り組むイシューを決定し、チームでコミットする

**進め方**
1. 前スプリントの未完了イシューを確認し、繰り越すか判断する
2. バックログから優先度の高いイシューをサイクルに追加する
3. 各イシューの見積もり（ストーリーポイント）を確認する
4. チームの総キャパシティ（ベロシティ）と照らし合わせてスコープを決める

**準備事項**
- 担当イシューの説明と要件が明確になっているか確認する
- 見積もりが入っていないイシューは事前に見積もりを入れておく

### デイリースタンドアップ

**実施タイミング**: 毎朝 9:30（15 分）

**話す内容**（各自 2〜3 分）
1. 昨日やったこと（Linear のイシュー ID を添えて）
2. 今日やること
3. ブロッカー・懸念事項

```
発言例:
「昨日は LIN-123 のバックエンド実装が完了し、PR をオープンしました。
 今日は LIN-124 のフロントエンド実装を始めます。
 特にブロッカーはありません。」
```

### スプリントレビュー

**実施タイミング**: スプリント最終日（金曜日）15:00〜16:00

**目的**: スプリントで完了した機能をデモし、フィードバックを得る

**進め方**
1. 完了したイシューを担当者がデモする（1 件 5 分程度）
2. ステークホルダーからフィードバックを受ける
3. フィードバックは新しいイシューとしてバックログに追加する

### レトロスペクティブ（振り返り）

**実施タイミング**: スプリント最終日（金曜日）16:00〜17:00

**目的**: チームのプロセスを継続的に改善する

**進め方（KPT 形式）**

| カテゴリ | 内容 |
|---|---|
| Keep（続けること） | 上手くいっていること |
| Problem（問題） | 改善が必要なこと |
| Try（試すこと） | 次のスプリントで試したいこと |

```
例:
Keep:   PR のサイズが小さくなり、レビューが速くなった
Problem: 見積もりと実績のズレが大きいイシューが多かった
Try:    見積もりの際にタスク分解を細かくする
```

## 7. レポートとメトリクス

### チームのメトリクスの見方

**確認場所**: Linear → チーム → 「Analytics」タブ

**主なメトリクス**

| メトリクス | 意味 | 健全な状態の目安 |
|---|---|---|
| ベロシティ | 1 スプリントで完了したポイント数 | 前スプリントから ±20% 以内 |
| サイクルタイム | イシューが `In Progress` → `Done` になるまでの日数 | 平均 3 日以内 |
| バーンダウン | スプリント内の残ポイントの推移 | スプリント末に 0 に近づく |
| リードタイム | イシュー作成から完了までの日数 | チームで定期的に確認する |

### スプリントレポートの確認

**確認場所**: Linear → サイクルを選択 → 「Report」タブ

```
スプリント #42 レポート
 完了: 14 イシュー（22 ポイント）
 未完了: 2 イシュー（4 ポイント）→ 次スプリントへ繰り越し
 スコープ追加: 1 イシュー（2 ポイント）
```

### メトリクスを活用した改善

- サイクルタイムが長いイシューはタスク分解が不十分な可能性がある
- ベロシティが安定しない場合はスプリント計画の精度を見直す
- `In Review` で長期間止まっているイシューはレビュープロセスに問題がある可能性

## 8. 演習

以下の演習を順番に実施してください。完了後、メンターに確認を依頼してください。

### 演習 1: イシューの作成

1. Linear を開き、自分のチームに移動する
2. 以下の内容でイシューを作成する

```
タイトル: [トレーニング演習] <your-name> のテストイシュー
説明:
  ## 目的
  Linear トレーニングの演習として作成したテストイシューです。

  ## 完了条件
  - [ ] イシューを作成した
  - [ ] ステータスを一通り変更した
  - [ ] GitHub ブランチと連携した

優先度: Low
ラベル: training
```

3. 作成したイシューの URL を控えておく

### 演習 2: ステータスの変更

作成したイシューのステータスを以下の順に変更し、各変更にコメントを残します。

```
Backlog → Todo
（コメント: スプリント計画でピックアップしました）

Todo → In Progress
（コメント: 作業を開始します）

In Progress → In Review
（コメント: GitHub PR: https://github.com/<org>/<repo>/pull/XXX）

In Review → Done
（コメント: PR がマージされました。作業完了です）
```

### 演習 3: GitHub ブランチとの連携

1. イシューを開く
2. 右上の「...」メニューから「Create branch」を選択する
3. 提案されたブランチ名を確認し、ターミナルで実行する
4. ブランチを作成した後、イシューに GitHub ブランチが表示されることを確認する

```bash
# Linear が提案するコマンドをそのまま実行する
git checkout -b training/lin-XXX-your-name-test-issue origin/develop
```

5. 空のコミットを作成して PR を開く

```bash
git commit --allow-empty -m "chore: トレーニング演習用のテスト PR"
git push origin training/lin-XXX-your-name-test-issue
```

6. GitHub で PR を作成し、説明に `Closes LIN-XXX` を記載する
7. Linear のイシューに PR が自動で紐付いていることを確認する

### 演習 4: スプリントへの追加（確認のみ）

現在進行中のサイクルを確認し、以下を確認します。

- 現在のサイクルの開始日と終了日
- チームのベロシティ（前スプリント比較）
- 自分に割り当てられているイシューの数とポイント

---

**演習完了後**

以下を Slack でメンターに共有してください。
- 作成したイシューの URL（Linear）
- ステータス変更の各コメントのスクリーンショット
- GitHub PR と連携したことを示すイシューの画面
