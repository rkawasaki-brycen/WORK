# ISMS / セキュリティ意識向上トレーニング

**対象:** チームメンバー全員
**所要時間:** 約45分
**年次再認定:** 本トレーニングは年に一度の受講が必要です
**更新日:** 2026-06-12

---

## はじめに

情報セキュリティは「セキュリティ担当者の仕事」ではありません。チームの全員が日常的なセキュリティ意識を持つことで、初めて組織全体の情報が守られます。

このトレーニングを完了した後、以下のことができるようになることを目標とします。

- 情報の機密レベルを正しく判断できる
- パスワードとシークレットを安全に管理できる
- フィッシング攻撃に気づいて適切に対応できる
- セキュリティインシデントを発見したら迷わず報告できる

## 1. 情報分類: 何が Public / Internal / Confidential / Restricted か

私たちが扱う情報はすべて 4 つのレベルに分類されます。詳細は `docs/isms/information-classification.md` を参照してください。

### 情報分類の一覧

| レベル | 説明 | 例 |
|--------|------|-----|
| **Public（公開）** | 外部公開を前提とした情報。漏洩しても実質的な損害が発生しない | 公開 Web サイトのコンテンツ、プレスリリース、オープンソースコード |
| **Internal（社内限定）** | 社内での業務に使う情報。外部への漏洩は望ましくないが、軽微な損害にとどまる | 社内会議の議事録、設計ドキュメント、社内ポリシー文書 |
| **Confidential（機密）** | 特定の関係者のみがアクセスすべき情報。漏洩すると重大な損害が生じる | 非公開ソースコード、顧客との契約書、財務情報、未修正の脆弱性情報 |
| **Restricted（極秘）** | 最高レベルの保護が必要な情報。漏洩すると回復困難な損害が生じる | APIキー・パスワード・秘密鍵、顧客の個人情報・決済情報 |

### 実際の判断フロー

情報の分類が分からない場合は、以下の手順で判断してください。

1. その情報が外部に公開されても問題ないか？ → YES なら **Public**
2. 社内の全員が業務上使う情報か？ → YES なら **Internal**
3. 特定の担当者だけが必要な情報か、顧客情報を含むか？ → YES なら **Confidential**
4. 認証情報・個人情報・決済情報を含むか？ → YES なら **Restricted**

**迷ったら上位の分類にする**（Internal か Confidential か迷ったら Confidential として扱う）。

### 情報分類別のハンドリングルール

| レベル | 保存 | 送信 | AI への送信 |
|--------|------|------|------------|
| Public | 制限なし | 制限なし | 許可 |
| Internal | 組織管理システムのみ | 組織の承認済み手段（Slack, メール等） | 原則許可 |
| Confidential | アクセス制御が必要なシステムのみ | 暗号化された通信路のみ | 事前承認が必要 |
| Restricted | 暗号化ストレージのみ（シークレット管理ツール必須） | 暗号化必須・メール原則禁止 | 禁止 |

## 2. パスワードとクレデンシャルの管理

### 2.1 強いパスワードの基準

| 要件 | 基準 |
|------|------|
| 長さ | 12文字以上（16文字以上を推奨） |
| 複雑性 | 大文字・小文字・数字・記号を各1文字以上 |
| 禁止 | 辞書の単語、氏名・誕生日、過去5回分と同じパスワード |
| 再利用 | サービスごとに異なるパスワードを使用 |

### 2.2 パスワードマネージャーは必須

全メンバーは**パスワードマネージャー（1Password、Bitwarden 等）の使用が必須**です。

- 各サービスにはパスワードマネージャーで生成したランダムパスワードを設定する
- チーム共有アカウントのパスワードは「共有ボルト」機能で管理する
- パスワードを Slack・メール・チャット等で共有することは**禁止**

### 2.3 多要素認証（MFA）の設定

以下のサービスには MFA の設定が**必須**です。

| サービス | 必須の MFA 方式 |
|---------|--------------|
| GitHub | TOTP（認証アプリ）またはハードウェアキー |
| AWS マネジメントコンソール | TOTP またはハードウェアキー |
| Google Workspace | TOTP または Google Prompt |
| パスワードマネージャー | TOTP + マスターパスワード |

MFA 方式の優先順位:
1. ハードウェアセキュリティキー（YubiKey 等）— 最も安全
2. 認証アプリ（Google Authenticator、Authy 等）— 標準
3. SMS — フィッシング耐性が低いため、可能な限り上位方式を使うこと

MFA のバックアップコードは**パスワードマネージャーに保存**し、メール・Slack等には送らないこと。

### 2.4 アカウント管理

- 退職者のアカウントは**退職日当日**に無効化します
- 自分のアカウントが不審な動作をしていると感じたら、直ちに Security 担当者に報告してください
- 共有アカウントは原則使用せず、個人アカウントを使用してください

## 3. シークレットの取り扱い: コードに書いてはいけない

### 3.1 絶対にやってはいけないこと

```python
# 禁止: コードにシークレットをハードコードする
API_KEY = "sk_live_xxxxxxxxxxxxxxxxxxxx"
DATABASE_URL = "postgresql://admin:password123@prod.example.com/db"
```

**一度コミットしたシークレットは Git 履歴に残ります。リポジトリを削除しない限り履歴から取り除くことはほぼ不可能です。プライベートリポジトリでも同様です。**

### 3.2 正しいシークレットの管理方法

**ローカル開発:** `.env` ファイルに記載し、`.gitignore` で除外する

```bash
# .env（Git にコミットしない）
DATABASE_URL=postgresql://user:password@localhost:5432/mydb
STRIPE_SECRET_KEY=sk_test_xxxxxxxxxxxx

# .env.example（Git にコミットする — ダミー値のみ）
DATABASE_URL=postgresql://user:password@localhost:5432/dbname
STRIPE_SECRET_KEY=sk_test_YOUR_KEY_HERE
```

**CI/CD・本番環境:** GitHub Secrets を使用する

```yaml
# GitHub Actions でシークレットを使う
jobs:
  deploy:
    steps:
      - name: Deploy
        env:
          API_KEY: ${{ secrets.PROD_API_KEY }}
        run: ./deploy.sh
```

GitHub Secrets への登録: `リポジトリ → Settings → Secrets and variables → Actions`

### 3.3 シークレットの命名規則

```
{環境プレフィックス}_{サービス名}_{種別}

例:
PROD_STRIPE_SECRET_KEY  — 本番環境の Stripe シークレットキー
STG_DATABASE_URL        — ステージング環境のデータベース URL
SLACK_WEBHOOK_URL       — Slack Webhook URL（環境非依存）
```

### 3.4 定期的なシークレットローテーション

| シークレット種別 | ローテーション周期 |
|----------------|----------------|
| パスワード（チームアカウント） | 90日 |
| APIキー（外部サービス） | 180日 |
| データベースパスワード | 90日 |
| TLS 証明書 | 有効期限の30日前 |

退職者が出た場合や、シークレットの漏洩が疑われる場合は**即時ローテーション**してください。

### 3.5 誤ってコミットしたときの対応

1. **直ちにそのシークレットを無効化する**（APIキーなら失効、パスワードなら変更）
2. `#security-incidents` Slack チャンネルに報告する
3. Tech Lead と Security 担当者に連絡する
4. Git 履歴からの削除作業は Tech Lead の指示に従って行う

「まだ誰も気づいていないはずだから大丈夫」という考えは危険です。**発見した時点で必ず報告してください。**

## 4. フィッシング攻撃への対策

### 4.1 フィッシングとは

フィッシングは、正規のサービス（GitHub、Google、銀行など）を装って、パスワードや個人情報を詐取する攻撃手法です。メール・SMS・電話（ビッシング）などさまざまな形で行われます。

### 4.2 フィッシングメールの見分け方

以下の特徴があれば疑ってください。

- **送信元メールアドレス**: ドメインが微妙に違う（`github.com` → `github-security.com`）
- **緊急性を煽る**: 「24時間以内に対応しないとアカウントが停止されます」
- **不審なリンク**: リンクにカーソルを当てた時の URL が正規ドメインでない
- **添付ファイル**: 予期していない添付ファイル（特に .exe, .zip, .docm 等）
- **個人情報・認証情報の要求**: メールでパスワードや MFA コードを要求することは正規のサービスはしない

### 4.3 フィッシングに遭遇したときの対応

```
1. リンクをクリックしない。添付ファイルを開かない。
2. 疑わしいメールは #security-alerts または Security 担当者に転送・報告する
3. 誤ってクリックしてしまった場合: 直ちに Security 担当者に報告し、パスワードを変更する
4. 判断に迷ったら「クリックしない」が正解
```

### 4.4 実際の訓練

会社が定期的にフィッシング訓練メールを送ることがあります。クリックしてしまっても罰則はありません。訓練の目的は習慣的な注意を身につけることです。

## 5. セキュアコーディングの基本

開発者向けの詳細は `docs/training/secure-coding-training.md` を参照してください。ここでは全員が知っておくべき基本事項を説明します。

### 5.1 入力は信頼しない

ユーザーやシステムから受け取った入力データはすべて悪意ある内容が含まれる可能性があると考えて処理してください。入力バリデーションを必ず実施し、想定外のデータをそのまま使用しないようにします。

### 5.2 エラーメッセージに情報を含めすぎない

```python
# 悪い例: スタックトレースやシステム情報を外部に返す
return {"error": traceback.format_exc()}

# 良い例: ユーザーには汎用的なメッセージ、詳細はログに記録
logger.error(f"DB connection failed: {e}")
return {"error": "Internal server error"}, 500
```

### 5.3 ログに機密情報を出力しない

```python
# 禁止: ログにパスワードや個人情報を出力する
logger.info(f"User login: email={email}, password={password}")

# 良い例: 機密情報はマスクする
logger.info(f"User login attempt: email={email}")
```

## 6. セキュリティインシデントを疑ったときの対応

### 6.1 インシデントとなりうる状況

- 不審なメールのリンクを誤ってクリックした
- パスワードを誤って共有してしまった
- シークレットをコードにコミットしてしまった
- 自分のアカウントで身に覚えのないアクティビティがある
- 本番環境に不審な動作がある
- データが意図せず外部に共有された可能性がある

### 6.2 報告先と手順

**報告チャンネル:**
- 緊急（P1/P2）: `#security-incidents` Slack + Security 担当者に電話
- 通常（P3/P4）: `#security-incidents` Slack

**報告内容（最低限）:**
```
- 何が起きたか（または起きたと思うか）
- いつ気づいたか
- すでに取った対応（あれば）
```

**大切な原則:**
- **即時報告**: 「大したことないかも」と思っても報告する。判断は Security 担当者が行います
- **隠さない**: 自分がミスをしたとしても、報告しなければ被害が拡大します。報告者は不当に不利益を受けません
- **証拠を保全**: インシデントに関連する機器・ログを勝手に削除・変更しないこと

### 6.3 インシデント優先度

| 優先度 | 例 | 対応開始目標 |
|--------|-----|------------|
| P1（緊急） | 顧客データへの不正アクセス、本番環境での認証情報の侵害 | 即時（15分以内） |
| P2（高） | 退職者アカウントによる不審アクセス、DDoS | 30分以内 |
| P3（中） | テスト環境への不正アクセス、フィッシングメール誤クリック（実害なし） | 4時間以内 |
| P4（低） | 脆弱なパスワードの発見、MFA 未設定アカウントの発見 | 翌営業日 |

## 7. 年次再認定について

本トレーニングは**年に一度の受講が必要**です。

- 受講後、確認テストを完了し、受講記録を残してください
- 新しいセキュリティポリシーが制定された場合は、年次サイクルに関わらず追加トレーニングが行われることがあります
- 未受講のメンバーは、Tech Lead から受講を促されます

セキュリティの脅威は常に変化します。年次トレーニングを通じて、最新の脅威と対策を継続的に学びましょう。

## まとめ: 毎日のセキュリティチェックリスト

```
朝のルーティン:
[ ] 不審なメールがないか確認し、怪しければ報告する
[ ] 身に覚えのないログイン通知がないか確認する

コーディング時:
[ ] シークレットをコードに書いていないか確認する
[ ] ログに個人情報・機密情報が含まれていないか確認する
[ ] コミット前に .env やシークレットファイルが含まれていないか確認する

PR レビュー時:
[ ] コードにシークレットがハードコードされていないか確認する
[ ] ログ出力に機密情報が含まれていないか確認する

退席時:
[ ] 画面をロックする（macOS: Command + Control + Q）
[ ] 公共の場でのスクリーンに注意する
```
